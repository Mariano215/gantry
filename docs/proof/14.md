# Proof 14, an approval releases a held call

## 1. The claim

The policy has three verdicts. Two of them worked.

`allow` executed, `deny` refused and named its rule, and `hold` recorded an
obligation and then died with this:

```
policy held Bash on git push origin main: rule r-publish gates this call pre
and no approval mechanism exists until slice 06
```

Slice 06 shipped. The message named a slice that had already landed, and
nothing in the system could produce the event it asked for. Approvals existed
only for rung promotion in `src/trust.rs`, never for a call. So every `hold`
rule in `config/policy.json` was decoration: the gate blocked, and there was
no way through it except editing the policy.

The claim now is that a held call is a call waiting for a human, and the
human's answer is on the record either way.

## 2. The attack

The happy path is the least interesting part, so it is last.

1. Approve a call the policy **denied**. It must be refused. An approval that
   can reverse a denial turns the whole policy into advice.
2. Refuse a held call. The refusal must be an event, and the call must stay
   held. "Nobody looked at this" and "somebody looked and said no" cannot be
   the same state.
3. Approve a held call and use it. The `policy.decision` must still read
   `hold`, because that is what the policy computed.
4. Use the same grant twice. The second attempt must be held.
5. Use a grant against a **different** call held under the same rule. It must
   not release it.
6. Consume a grant whose approver the trust budget does not permit. It must
   not release anything, even though the grant is on the ledger.

## 3. What happened

Run against a real ledger, not reasoned about. Commands and output verbatim.

**Attack 1, approving a denial:**

```
$ gantry broker call /tmp/p14/led Bash "rm -rf /"
$ gantry approve /tmp/p14/led run-1785932796363-req-3 user:mariano@local
request run-1785932796363-req-3 resolved to deny, and only a held call can be
approved. Fix: an approval releases a call the policy held pre-execution; it
never reverses a denial. Change the policy rule if the call should be
permitted at all.
```

**Attack 2, a recorded refusal:**

```
$ gantry approve /tmp/p14/led run-1785932795831-req-3 user:mariano@local deny
approval run-1785932797270-0: user:mariano@local recorded deny for rule
r-publish on request run-1785932795831-req-3
the refusal is on the ledger; the call stays held and nothing releases it

$ gantry broker call /tmp/p14/led Bash "git push origin main"
policy held Bash on git push origin main: rule r-publish gates this call pre
and no approval on this ledger releases it.
```

**Attacks 3 and 4, approve, use, then try again:**

```
$ gantry approve /tmp/p14/led run-1785932795831-req-3 user:mariano@local
approval run-1785932807268-0: user:mariano@local recorded approve for rule
r-publish on request run-1785932795831-req-3
it releases one call whose hash is sha256:2508e9138c09b81... make the same
call again to use it

$ gantry broker call /tmp/p14/led Bash "git push origin main"
[taint: true] (ledger sealed at size 33)

$ gantry broker call /tmp/p14/led Bash "git push origin main"
policy held Bash on git push origin main: rule r-publish gates this call pre
and no approval on this ledger releases it.
```

The whole arc, read off the ledger afterwards:

```
policy.decision  hold r-publish
tool.result      blocked
policy.decision  deny r-destructive-shell
tool.result      denied
approval         deny by user:mariano@local
policy.decision  hold r-publish
tool.result      blocked
approval         approve by user:mariano@local
policy.decision  hold r-publish
approval.use     spent run-1785932807268-0 self_approved=True
tool.result      ok
policy.decision  hold r-publish
tool.result      blocked
```

Read it top to bottom: the policy held, a human said no, it stayed held, a
human said yes, the grant was spent, the call ran, and the next attempt was
held again. Forty entries, all attested, and the head verifies.

Attacks 5 and 6 are covered by `tests/broker.rs`
(`an_approval_does_not_release_a_different_call`,
`a_grant_from_an_unpermitted_approver_does_not_release_the_call`) rather than
by hand, because both need two policies over one ledger.

## 4. What surprised you

**The request id is the wrong handle, and it took building it to see why.**
The obvious design has the approver name the request they are answering, and
the broker look for a grant with that request id. It does not work. Every
`gantry broker call` opens a new run, so the retry of a held call carries a
new request id, and the grant would name a request that will never be made
again. An approval bound to the request id is an approval for nothing.

So a grant names the call hash, the canonical hash of the tool and its
arguments, which is stable across runs. The request id is still recorded, as
provenance, because it is what the approver actually saw. The lesson
generalises: the thing a human points at and the thing the machine matches on
are not always the same thing, and binding to the first is the natural mistake.

**The decision must keep saying hold.** The tempting implementation rewrites
the decision to `allow` once the approval is found, and it is wrong for the
reason this project exists. The policy held that call. An `allow` on the
record would say the policy permitted something it did not, and a reader
auditing decisions would never see that a human was involved. The hold stays,
and the release is a separate `approval.use`. This is the same shape as the
sensor bus recording `broken` rather than folding it into `fail`: the record
distinguishes states that a summary would merge.

**The event schema had already specified this, and nothing implemented it.**
`docs/EVENT-SCHEMA.md` carried an `approval` kind with
`verdict (approve, deny)` and the note "A human refusing is an approval with
`verdict: deny`, not an absent event (finding 5)". That row had been sitting
there since slice 01. The first implementation of this work invented
`approval.grant` beside it and left the declared kind unimplemented, which
would have made the schema half fiction: one row describing what runs, one row
describing what somebody once intended. Aligning to the declared kind is what
added the deny verdict, which was not in the original plan for this work and
is the better half of it.

**Permission has to be re-derived where the grant is used.** `gantry approve`
refuses an approver the trust budget does not permit, and that check is not
worth much on its own. A ledger is a file. Anything that can write the file
can append an `approval` claiming any approver it likes. The consuming end in
`src/broker.rs` re-checks against the trust budget rather than trusting that
the event exists, and that is the check that carries the weight.

## 5. Conformance delta

**No primitive moved, and the reason is worth stating precisely.**

`docs/PRIMITIVES.md` says primitive 07 is strong when there is "a defined
lifecycle with human gates at irreversible steps". That is now what runs:
`r-publish` gates an irreversible effect before execution, and a human
resolves it on the record. By the rubric, this is the thing.

The scorer does not credit it, because `config/scoring.json` has no level 4
for primitive 07 at all. Its levels stop at 3. So orchestration still scores 3
and the overall stays 3.

Adding that rule is deliberately **not** part of this work. Proof 13 records
what happens when a scoring rule is written in the same breath as the feature
it scores: the first instruction-lifecycle rule paid for the sensor's failure
rather than its running, and the inversion was invisible until the score
failed to move. A level 4 for orchestration has to name the control running,
which here means an `approval.use` on the record, and `docs/proof/08-run.sh`
has to exercise a held-and-approved call, or the rule lands and nothing
changes. Both are a separate piece of work with their own adversarial case.

The number staying at 3 while the layer got stronger is the arithmetic
working, and it is the fourth time this has happened in this project.

## 6. What is still a guide

- **No approval inbox.** The console is read only by decision, so an approver
  finds held calls by reading the ledger view and grants from the CLI. The
  console can show a held call; it cannot be the thing you click. That is the
  right default until there is an identity story for a write path, and it is
  the same reasoning that kept the API read only in proof 10.
- **Self-approval is permitted and merely recorded.** On the laptop profile
  `trust_budget.promotion.approver` is `any`, so the caller can approve their
  own call. `approval.use` carries `self_approved: true` when they do, so it
  is visible rather than hidden, but nothing refuses it. A profile that wants
  four eyes sets `approver: named` and leaves the agent's identity off the
  list. Whether self-approval should be refusable independently of the named
  list is an open question.
- **The approver set is borrowed from promotion.**
  `trust_budget.promotion.approver` governs both rung promotion and call
  approval. That is one concept doing two jobs, which is right until somebody
  needs the sets to differ, and then it is a schema change.
- **A grant does not expire.** It is single use and bound to one call, but it
  sits on the ledger until something spends it. A grant approved on Monday
  releases the same call on Friday. Time-bounding it needs a clock the ledger
  does not currently trust for this purpose.
- **`gantry approve` reads `config/policy.json` from the working directory,**
  like the other subcommands, so approving against a harness elsewhere means
  running from that harness. The broker has the same constraint; it is not new
  here, and it is the reason the tests invoke the binary with an explicit
  working directory.

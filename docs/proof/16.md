# Proof 16, gantry scan reads a repository and flatters nobody

## 1. The claim

`CLAUDE.md` opens by saying a rule with no enforcing check is marked
`[UNENFORCED]`, and that "`gantry scan` on this repo is expected to report it".
`docs/CLAUDE-CODE-INTEGRATION.md` called `gantry scan` the growth engine and
said to design it first. Neither was true: there was no such subcommand, and
`docs/GLOSSARY.md` listed it under "declared, not enforced". The rule file
promised a command that did not exist, which is the exact defect its own
opening paragraph describes.

`gantry scan <repo-dir>` now exists, and the claim is four things:

1. It reads and writes nothing. Not by intention, by shape: every filesystem
   call in `src/scan.rs` goes through `RepoRead`, which has no write, create,
   rename or remove.
2. Every one of the twelve numbers carries a path. A score of 0 names every
   path that was looked in and came back empty, which is the harder half.
3. It reports the `[UNENFORCED]` markers the scanned repository's own rule file
   carries.
4. It does not flatter this repository. A static read measures the presence of
   a control, never the control running, so it caps at 3, it says so in its own
   output, and on this repository it lands at or below the telemetry score on
   all twelve primitives.

## 2. The attack

The interesting failure of a scanner is not a crash. It is a number that looks
like a measurement and is a compliment. So:

1. Point it at an empty directory. Every primitive must score 0 and must name
   the paths it looked in. A scanner that reports 0 with no path behind it is
   the thing `docs/PRIMITIVES.md` calls an opinion.
2. Point it at this repository and compare every primitive against the live
   telemetry score from `zsh docs/proof/08-run.sh`. Any primitive where the
   static number exceeds the telemetry number is a bug in the scanner, because
   files are the weaker evidence.
3. Point it at this repository and prove the tree is untouched afterwards:
   every path, mtime and size identical, and `git status` unchanged.
4. Feed it a repository whose CI mentions a control in a comment. A comment is
   not a check. A scanner that credits prose scores well-commented repositories,
   and this one is very well commented.
5. Break the scanner so it emits a score with no evidence, and watch the new CI
   check go red. A check never seen red is a dead sensor reporting green.
6. Break the path so the scan cannot run, and watch the same check go red for
   the other reason.

Reproduce with:

```
cargo build
./target/debug/gantry scan .
cargo test --test scan
zsh ci/run.sh
```

```

$ ./target/debug/gantry scan . > /dev/null

```

`git status --porcelain` after the scan lists only the files this slice edits.
The same property is asserted twice in `tests/scan.rs`, once against the
running scan (`a_scan_never_writes_to_the_target`, byte and mtime snapshot
before and after) and once against the module's shape
(`the_scanner_holds_no_write_capable_filesystem_call`, which fails the build if
`src/scan.rs` ever references `fs::write`, `File::create`, `OpenOptions`,
`create_dir`, `remove_file`, `remove_dir`, `fs::rename`, `fs::copy`,
`set_permissions` or either link call). The behavioural test alone would pass
for a scanner that writes only on a branch the fixture does not reach.

Note also what the subcommand does **not** do: unlike `gantry score`, it
appends nothing to a ledger. A scan of somebody else's repository has no ledger
to append to, and writing one into their tree would break the same property.

## 4. What surprised you

**The `[UNENFORCED]` convention is only half machine-readable, and the scan
says so about the file that defines it.** `CLAUDE.md:17` reads "Rules with no
enforcement yet are marked `[UNENFORCED]`", which is the paragraph defining the
convention, and it is indistinguishable by text from a use of it. The real
marker at `CLAUDE.md:158` puts the check id in backticks on the *next* line,
because the paragraph wrapped. So a scanner either misses real markers, or
reports the definition as one. This one reads the marker line and the line
after it, accepts a backticked token as a check id only when it has no
whitespace and a separator in it, and reports a marker with no check id as
exactly that: a marker where nothing says what would close it. That is the
honest output for line 17 and it is also a fair complaint, since a convention
whose definition reads as an instance of itself is one a machine cannot count.
The fix belongs in `CLAUDE.md`, not here, and it is one line: write markers as
`` `[UNENFORCED]` `ci/check-name` `` on a single line, and phrase the defining
paragraph without the literal token.

**The scan disagrees with the telemetry score on ten of twelve primitives, and
that is the result rather than a defect.** The temptation while writing the
probe table was to teach it this repository's layout, at which point primitive
11 would have found `src/ledger.rs` and scored 3, and 04 would have found the
broker registry. Every one of those additions would have been a rule that fires
on gantry and on nothing else, which is a compliment with a file path attached.
The probe table holds only conventions other repositories use, and the price is
that gantry, whose harness is mostly running code rather than tracked
configuration, scores 0 on four primitives. Primitive 11 is the sharpest case:
the recorder is the strongest layer in this system and a clean checkout shows
none of it, because a ledger is runtime state. A scanner that could see it
would be reading something other than files.

**Two numbers, and the smaller one is the more honest of the two about its own
limits.** The static overall of 0 is not a claim that this repository is
ungoverned; it is a claim that four of its twelve layers leave nothing in a
file tree. The telemetry overall of 3 is a claim about 137 events. The output
says which is which, in the report itself rather than only in a document,
because the scan is the artifact people post and it will be read without this
proof beside it.

## 5. Conformance delta

**No primitive moved, and this time the reason is that nothing about the
running system changed.** `gantry scan` reads other people's repositories. It
appends no event, so `config/scoring.json` has nothing new to score and the
telemetry overall stays 3.

What moved is the count of rules in `CLAUDE.md` that name a check which does
not exist. The opening paragraph's promise ("`gantry scan` on this repo is
expected to report it") was unenforceable for sixteen slices, because there was
no `gantry scan`. It runs on every push now, and it reports two markers rather
than the one a reader would expect, which is a finding about the marker
convention rather than about the sensor placement work item.

`docs/GLOSSARY.md`'s "declared, not enforced" list loses `gantry scan` and
keeps `gantry apply` and `gantry up`. `docs/CLAUDE-CODE-INTEGRATION.md`'s
onboarding table now carries a state column, so the two unbuilt commands are
marked unbuilt in the table that describes them rather than only in the
glossary.

## 6. What is still a guide

- **Marker matching is substring matching.** A check file counts as naming a
  primitive when its non-comment text contains one of that primitive's markers.
  `ci/console-render.sh` credits primitive 12 because it contains
  `policy.decision`, which is true but incidental. The evidence line names the
  file and the exact string, so a reader can overrule it in a second; parsing
  each CI dialect properly is the upgrade path and it is not worth its weight
  until somebody is misled by a match.
- **Only CI and hook configuration count as check files.** A check that lives
  in a test file is invisible: this repository's `tests/sandbox.rs` really does
  gate the sandbox, and primitive 05 scores 2 anyway, because `cargo test` in
  `ci/run.sh` naming "test" is not a statement about the sandbox. Under-reading
  is the safe direction for a tool whose failure mode is flattery.
- **The probe table is one practitioner's list of conventions.** A repository
  that keeps its agent instructions somewhere the table does not name scores 0
  on primitive 01 with a "looked in" line that omits the path it actually uses.
  The evidence format makes that argument possible, which is the point: the
  first thing a reader does with a low score is name the file the scan missed,
  and that is a better conversation than a number with nothing behind it.
- **No N/A.** The rubric says a primitive the workload never exercises scores
  N/A rather than 0, and a static read cannot tell "no sub-agents needed" from
  "sub-agents missing". Every absent primitive scores 0 and the ceiling
  paragraph says why. `gantry score` still awards N/A, since a ledger shows
  which primitives the workload actually touched.
- **`gantry apply` and `gantry up` are still unbuilt**, and remain listed as
  such. The scan produces a ranked gap list only in the sense that the table is
  sorted by primitive; the rubric's remediation order is not applied and no
  diff is offered.

## 8. What the merge changed

One defect in this scanner surfaced at merge, when `CLAUDE.md` was rewritten to
the one-line marker form this proof recommends, and it is recorded here rather
than edited into the run above.

`check_id` took the first backtick-delimited pair after the marker. A rule file
writes the marker itself in backticks, so the fragment after `[UNENFORCED]`
opens with that marker's own closing backtick, every quoted token after it read
on the wrong parity, and the first pair resolved to the empty gap between the
marker and the id. The function then fell through to the next-line branch. The
effect was worse than a miss: for the one marker that already named a check,
the fallback returned `docs/proof/05.md`, the next path in the paragraph, and
reported it as the check that would close the rule. The two new markers landing
in the same merge reported no check id at all, though both name one on their
own line.

The parse now strips the marker's own closing backtick before splitting and
scans the quoted segments for the first that looks like an id, so the marker's
own line wins and the wrapped fallback fires only when that line names nothing.
`a_check_id_is_read_off_the_marker_line_or_the_next_one` gained the two shapes
a rule file actually writes. All three markers in `CLAUDE.md` now resolve:
`ci/sensor-placement-honoured`, `ci/egress-allowlist-observed`,
`ci/anchor-schedule`.

The test that caught it was this proof's own
`scanning_this_repository_stays_under_its_own_ceiling_and_reports_its_markers`,
which asserts the scan reports the marker `CLAUDE.md` carries. It failed on the
merge commit, which is the check doing its job on a file it was not written
against.

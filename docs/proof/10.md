# Proof 10, attested events and a read-only console API

## 1. The claim

Two halves that share a proof because the second is worthless without the
first: a UI that renders the ledger is only as trustworthy as the signatures
on the rows it renders.

**Attestation.** Before this slice, `ledger::verify_with_actor_keys` checked
actor attestations against `config/actor-keys.json` and both branches were
exercised by tests, but no producer emitted one. Every envelope the gateway
and broker appended carried `attestation: null`. `CLAUDE.md` said so out loud.
A verification path that only tests reach is the defect this project exists to
catch, found in this project.

Now the profile declares its actor key in
`config/policy.json` under `profile_requirements.attestation`, and `RunCore`
signs every event the gateway and broker append over
`Envelope::attestation_bytes`. A profile that declares a key it cannot load,
or whose seed produces a different key id than declared, refuses the run
rather than appending unsigned.

**API.** Eight read-only routes over the ledger, implementing
`docs/CONSOLE-API.md`, standard library only, no new dependency. Read-only by
decision: a UI that can move a rung is an authority surface and the laptop
profile has no identity story for one.

## 2. The attack

1. Run the broker for real and verify the resulting ledger. Every event must
   report as verified, not counted.
2. Alter a signed event after the fact. The verifier must name it as
   alteration, not pass it.
3. Declare a key the profile cannot load. The run must refuse before
   appending anything, never degrade to unsigned.
4. Serve a ledger and read every route. Shapes must match the contract.
5. Mutate a stored event under a running server. `/api/verify` must return
   `ok: false` on the next request, because nothing is cached.
6. The adversarial case this slice added, found during integration: check
   what a verified attestation is actually worth.

## 3. What happened

A real broker run, then verification:

```
$ gantry broker call /tmp/merged Read README.md
$ gantry ledger verify /tmp/merged
entries: 14
attestations verified against config/actor-keys.json: 14
of those, 14 were signed under a key whose seed is published, so they prove which run wrote the event and not who operated it; a deployment registers its own key and keeps the seed
```

Before this slice the second and third lines did not exist. The third line is
the finding, and section 4 is about it.

Every route, served from the binary against a 137-event ledger built by
`docs/proof/08-run.sh`:

```
/api/score      overall 3, primitive 1 at 4
/api/head       size 137, root sha256:a866c75a8ae7240423f3f59f9e70da9494794d44e060691c9707c1abbc38e80e
/api/verify     ok true, verified 33, under published seed 33
/api/runs       33 runs
/api/trust      5 capabilities
/api/policy     8 rules, 2 with a non-zero fire count
/api/events     _attestation_state and _attestation_trust on every row
```

Tampering, with the server already running. One event's `ts` rewritten by
hand, no restart:

```
$ gantry ledger verify /tmp/tampered
entries: 137
attestations verified against config/actor-keys.json: 32
entry 7 (run-1785927265578-3): chain diverges between entry 7 and entry 8 ... Fix: entry 7 was altered after append; restore it from a replica
```

The API agreed on the next request, and the console rendered the failure
rather than the overview. That screenshot is in proof 11.

Three faults surfaced from one edit: the hash chain diverged, the Merkle root
no longer matched the signed head, and the attestation on entry 7 no longer
verified. The third of those exists only because of the first half of this
slice.

## 4. What surprised you

**A verified signature was not worth what the word implies, and every
reporting path said otherwise.**

The tracked laptop key's seed lives at `config/actor-key-fixture.seed`, which
is correct for a laptop profile: it lets a fresh checkout produce signed runs
with no key ceremony. The registry entry described this honestly in its
`owner` string.

Nothing downstream carried it. `gantry ledger verify` printed
`attestations verified against config/actor-keys.json: 14`, which reads as
attribution, and which is byte-identical to what a deployment with an
HSM-held key would print. The API returned a bare `"verified"`. A console
built on that would have shown a green badge on a signature anyone holding
the repository can forge.

This is the "profiles never lie" invariant failing at the reporting layer.
The invariant was enforced where the scorer reads and nowhere else, and it
took integrating two independently correct halves to make it visible: the
producer was right, the verifier was right, and the sentence they produced
together was wrong.

The fix is small and the lesson is not. A registry entry declares
`seed_published`, `VerifyReport` counts those attestations apart, the CLI
qualifies its count, and the API carries `_attestation_trust` of `registered`
or `fixture` beside the state. `tests/broker.rs`
(`a_verified_attestation_under_a_published_seed_is_counted_apart`) asserts the
count follows the registry's declaration and is never inferred.

Second surprise, smaller: the pre-existing console handler read at most 1024
bytes of the request and routed on whatever landed there, so a long query
string silently became a different query. The rewritten reader takes the head
whole to a 64 KiB cap and refuses past it, draining the socket first so the
client receives the refusal instead of a connection reset.

## 5. Conformance delta

Primitive 11 (Observability) and 12 (Governance): the record now carries a
signature from the actor that produced it rather than only the ledger's own
tree-head signature. The scorer's rules do not yet credit this, so neither
number moves, which is correct. A rule that credited it would need to
distinguish `registered` from `fixture`, or it would pay a laptop profile for
a signature anyone can produce.

No primitive moved on this slice. The layers got stronger and the numbers did
not, which is what the arithmetic is supposed to do.

## 6. What is still a guide

The laptop profile ships a published seed, so laptop attestations are
provenance and not attribution. That much is still true. What is no longer a
guide is the enforcement: the check this section asked for was written after
the proof landed. `ActorSigner::declared` reads the actor key registry beside
the policy and refuses any profile other than `laptop` that declares a key
marked `seed_published`, before the run appends its first event.
`tests/broker.rs`
(`a_non_laptop_profile_declaring_a_published_seed_refuses_to_start`) takes the
tracked policy, sets `profile` to `regulated` and asserts the refusal names
the profile and the reason, then flips the same document back to `laptop` and
asserts it opens, so the refusal is about the profile and not about the key
being unusable.

The gateway was reading the profile as the literal `laptop` at run open, which
would have exempted a non-laptop gateway run from this check and stamped the
wrong profile on `run.open` besides. It now reads the profile off the pinned
policy document, the same read that supplies the attestation block.

One case is deliberately not refused: a registry that is absent or unloadable
answers "not published", so the guard passes. That is not a hole. A run
signing under a key no registry lists verifies as unverified rather than as a
pass, so the failure is already visible in the report. The guard covers the
case the registry does describe, where the declaration and the profile
contradict each other.

`templates/laptop/config/policy.json` declares no actor key, and it still does.
What changed is what happens at init. The choice this section recorded was
between a template that ships the repository's own published seed, handing
every install on earth the same signing key, and a template that ships none,
producing a harness that appends unsigned. Unsigned was the more honest of the
two and neither was the answer. The answer named here as future work, key
generation at init, is now what runs.

`gantry template init` generates a fresh 32-byte seed from OS entropy, writes
it beside the copied policy at `config/actor-key.seed` with mode 0600,
registers the public half in a `config/actor-keys.json` the template does not
contain, with an owner naming the harness and `seed_published` false, and
writes `profile_requirements.attestation` into the destination policy
declaring `ed25519`, the key id that seed produces, `GANTRY_ACTOR_SEED` and
that seed file. The template itself stays free of key material: a tracked
declaration would have to name either tracked key material, which is the
failure being closed, or a key the bundle does not hold, which validates as a
template and refuses as a harness.

The write order is the part worth stating. Every destination path, copied or
generated, is checked before anything is written, so a refused init leaves no
half-written harness. Within the writes the seed goes last, after the policy,
after the policy is re-loaded through the same validator, and after the
registry. Any earlier failure therefore leaves a harness that refuses to run
because its declared key has no seed, which is loud, rather than a private key
sitting in a directory nobody finished building, which looks like a held key
and belongs to nothing.

Evidence, on a harness initialised into a temporary directory:

```
$ gantry template init templates/laptop /tmp/h
...
wrote /tmp/h/config/actor-keys.json
wrote /tmp/h/config/actor-key.seed (mode 0600)
harness initialised at /tmp/h from template templates/laptop, signing as ed25519:715c6683d340e9b1

$ cd /tmp/h && gantry broker call .ledger Read instructions/pack.md
$ gantry ledger verify .ledger
entries: 7
attestations verified against config/actor-keys.json: 7
```

Seven of seven verified, and no published-seed line, which is the line the
tracked laptop harness prints and the whole reason this was not solved by
copying its key. `tests/broker.rs`
(`template_init_generates_a_per_harness_key_and_the_harness_signs`) asserts
two inits produce two key ids, that the destination validates as a bundle in
its own right, and that the run verifies against the generated registry with
zero unverified and zero under a published seed;
`a_refused_init_leaves_no_seed_and_never_clobbers_one` asserts the refusal
ordering. `ci/run.sh` runs the same init and verify on every push.

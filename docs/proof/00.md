# Proof 00, schemas before code

**Note on verbatim output.** While this document was being written, the
repository's prose sensor (`ghost`) blocked the em dash and en dash characters
in every file write, including writes of this file. Quoted evidence below
therefore renders them as `[U+2014]` and `[U+2013]`. That substitution is the
only edit made to any verbatim output here, and it is kept after the sensor was
rescoped (finding (h)) because the trace should read the same way it was
written.

## 1. The claim

The event schema and the policy schema can express a real agent run end to end,
by hand, including a denial and an approval, well enough that a stranger can
reconstruct the run from the trace alone. Where they cannot, the gap is named
here rather than discovered after the ledger is written.

## 2. The attack

Slice 00 has no code, so the attack is not a tampered record. It is the
schema's own load-bearing claim: that this envelope is sufficient. The attack
is to take a real run, refuse to simplify it, and write every event by hand
without inventing a field.

The run chosen is this session itself: the slice 00 working session in
`/Volumes/T7/Projects/gantry`, run under Claude Code with
`.claude/settings.json` as the declared authority. It was chosen because it
contains three things a happy path does not.

- A **denial by permission rule**. The run needed the crates.io answer to the
  open name-collision question in `docs/CONCEPT.md`, and `Bash(curl:*)` sits in
  the `deny` list.
- A **denial by sensor**. The `ghost` PreToolUse hook blocked the first write of
  `docs/POLICY-SCHEMA.md`.
- A **human approval**. Two policy questions were put to the operator and
  answered.

Exact commands, both reproducible from the repository as committed:

```
# denial by permission rule
curl -s https://crates.io/api/v1/crates/gantry

# denial by sensor, then the approved retry
Write docs/POLICY-SCHEMA.md          # first attempt contained four em dashes
```

The primary evidence is the harness's own transcript, which is where a stranger
should go to check this document:

```

```

### 3.3 Findings from writing the trace

**(a) Every event in a real run carries `declared: false`.** The permission
mode running was `bypassPermissions` while the tracked file declared allow, ask
and deny lists. Per the event schema this caps primitive 12 at 2 for the whole
run. It is the rubric's worked-example failure reproduced exactly: the
authority was real, the declaration was tracked, and no check compared them.
The comment inside `.claude/settings.json` warns against this precise mistake.
Recorded as a finding at the operator's direction; the mode was not changed.

**(b) Twenty-two tool calls produced no decision.** The policy schema's first
constraint says every call is evaluated and emits exactly one
`policy.decision`. In the observed run, calls matching the `allow` list emit
nothing. Under the schema, an absent decision is a fault, so a faithful trace
of this run is 22 faults deep before it reaches anything interesting. Either
allows are recorded, in which case the ledger is mostly allows, or the schema
softens to "every call that is not an unconditional allow". Recording all of
them is the correct answer, and it is a volume problem for slice 01 rather than
a schema problem.

**(c) The denial that fired left no rule name.** A `deny` entry in the host
permission list short-circuits before the PreToolUse hook runs. The harness
recorded `toolDenialKind: "permission-rule"` and an error string, and nothing
else. `docs/CLAUDE-CODE-INTEGRATION.md` states that the pre-tool hook carries
the policy decision. For denials on this harness, that is false. The event at
seq 3 is reconstructed by hand from a settings file, which is not evidence.
This is enforcement without evidence: primitive 05 gets the benefit, primitive
12 gets nothing.

**(d) The approval gate produced no approval.** The `ask` entry on `Write(**)`
is in the tracked file. The write blocked for 1775.96 seconds. The transcript
records the request and the result and nothing in between: no approver, no
verdict, no elapsed time, no record that a human was involved at all. The only
reason this document can state 1775.96 seconds is arithmetic on two
timestamps. An approval that leaves no record is not an approval, and the
`approval` event kind is currently unproducible from this socket. The approval
at seq 9 exists only because the run took its questions to a tool that writes
its answers into the transcript.

**(e) `tool.call` cannot be emitted for a call that never returns.** The
envelope carries the request and the result in one event, so nothing can be
written until the call completes. A call blocked at a gate, a call that hangs,
and a call killed with the container are all indistinguishable from a call that
was never made. The 29 minute write is the live case: for those 29 minutes the
ledger would have been silent about the most interesting thing happening in the
run. This is the schema's most serious structural defect and it is why seq 7
carries two fields that do not exist in the schema.

**(f) Ordering by `seq` and ordering by `ts` are not the same order.** Two tool
calls issued in one assistant turn at `16:50:36.754Z` and `16:50:36.780Z`
returned results in the opposite order. The schema says `seq` is monotonic
within a run and offers `parent_id` as the only causal link. It has no way to
say two calls were concurrent, which means a reader cannot distinguish
concurrency from a recording gap.

**(g) The name collision question is still open, and the denial is why.** The
crates.io lookup was the run's reason for reaching the network. It was denied
correctly. The question recorded at the end of `docs/CONCEPT.md` remains
unanswered and does not block slice 00. This is what the policy schema's deny
message means when it says to perform the lookup outside the run and paste the
result.

**(h) A guide instructed an action a sensor forbade.** The `/proof` command
requires marking new unenforced checks in `CLAUDE.md`, and the `ghost` sensor
blocked every write to that file. Recorded in full in section 6, because the
resolution belongs with the checks it concerns.

## 4. What surprised me

Three things, none predicted.

**The blocking sensor worked and the governance layer did not.** The `ghost`
hook caught four em dashes in a document nobody had read yet, named the fix in
a form the agent could act on, and the retry passed. That is a level 4 control
doing its job on the first attempt. In the same run, the permission system
denied a command and the approval gate blocked a write, and neither left a
record naming a rule or a person. The layer with the crude regex is the mature
one here.

**The proof document had to argue with the file that authorises it.**
`.claude/settings.json` contains a comment saying its values must not move to
an untracked local file, because that is the exact failure the rubric
documents. The failure that actually occurred is adjacent and worse: the values
did not move, they were overridden wholesale by a runtime mode that no file
records. Nothing in the design anticipated a permission mode as a drift
dimension. `host_permissions` in `docs/POLICY-SCHEMA.md` was written before
this was observed and hashes the settings file, which would have reported a
clean match throughout this run.

**Writing the trace found more schema defects than reading the schema did.**
The critique produced before the trace named the retention contradiction and
the signature ordering problem. Findings (c), (d), (e) and (f) came only from
trying to write down what actually happened, and (e) is the one that would have
cost the most to discover after the ledger existed. The instruction to write
the trace by hand before writing code was the correct call and it paid within
one session.

## 7. Schema changes this proof requires before slice 01

Slice 01 writes the ledger, so these are decided now or they become migrations.

1. **Split `tool.call` into `tool.request` and `tool.result`,** linked by
   request id. Finding (e). Without this the ledger cannot record a call that
   blocked, hung, or died, which is the class of call an auditor most wants.
2. **Move `subject` out of the signed envelope, behind `subject_hash`.**
   Constraint 4 says a payload expires while its hash is retained. Constraint 2
   says the canonical form of the whole event is signed. Both cannot hold with
   `subject` inline: expiring it changes the event hash and breaks the chain.
3. **Two signatures, not one.** Constraint 3 signs the actor's event including
   `prev_hash`, but `prev_hash` is only known once the ledger accepts the
   entry. Either the actor round-trips before signing, or the ledger signs and
   `sig.key_id` names the ledger rather than the actor, which loses
   attribution. Separate an actor attestation over `subject_hash` from a ledger
   signature over position.
4. **`authority.declared` becomes a list of diverging fields, not a boolean.**
   Finding (a) diverged on permission mode while policy and instruction pack
   matched. A boolean cannot say which, and the reader of one event should not
   have to find a `drift.report` to learn it.
5. **Add `ledger.anchor`, `retention.expire` and `tool.register`, and give
   `approval` a verdict field.** An expiry is an act under someone's authority
   and must be an event. A human refusing is an approval with `verdict: deny`,
   not an absent event, for the same reason the schema already gives for policy
   denials.
6. **Define the leaf hash.** The document promises inclusion proofs without
   stating the RFC 6962 leaf prefix or the canonicalisation profile. A stranger
   cannot verify what is not written down, and slice 01's proof depends on
   exactly that.

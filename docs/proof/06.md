# Proof 06, orchestrator and trust budget

## 1. The claim

A capability earns its way from assisted to autonomous on a real run of
clean sensor history, promoted by a named approver whose approval is on the
ledger before the change it authorises, and is demoted one rung
automatically by the next sensor failure; the rung it holds at any point is
never stored, only replayed from the signed event log, so a third party
derives it themselves.

## 2. The attack

The adversarial case is trust that cannot be walked back: a capability that
reaches autonomous and stays there through a failure, or a rung asserted by a
field nobody can recompute. Executed by `docs/proof/06-run.sh` and
`tests/trust.rs`.

1. Run the `repo.write` capability's sensor (`no-private-key`) against a
   clean findings document `runs_at_rung` times (20, from the tracked
   `config/policy.json`). Promotion must fire on exactly the 20th clean run,
   not before, and must carry the approver identity.
2. Then run once against a document with an embedded private key. The sensor
   fails and the capability must demote from autonomous back to assisted
   automatically, with no approver.
3. Read the whole arc back out of the ledger with `gantry trust history`.

The suite pins the boundaries the script cannot show cheaply:
`tests/trust.rs` uses a demo policy with threshold 3 and an `approver: named`
budget to assert that promotion fires on the third clean run and not the
second, that an unpermitted approver is refused, that an earned promotion
with no approver is refused, that the approval event precedes the
`rung.change`, and that a counter resets on both a rung change and a failure.
`src/trust.rs` unit tests pin the replay arithmetic.

Reproduce with:

```
cargo build
zsh docs/proof/06-run.sh
```

## 4. What surprised me

**The rung being derived, not stored, is what made the proof honest, and it
exposed a parallel-test race the moment it existed.** Because every step
recomputes the rung by replaying the whole ledger, two orchestrator runs
opened in the same millisecond shared a run id, and their per-run sandbox
scratch directories collided: one test's negative-control file (which
contains a private key marker) was read as another test's clean artifact, so
a clean run recorded a failure and demoted a capability that should have been
promoting. The fix was a process-unique atomic suffix on every sandbox
workdir, not a change to the trust logic. The trust logic was right; the
shared-state bug was one layer down, and only surfaced because replay reads
real files rather than trusting an in-memory counter.

**Promotion refuses to be automatic even when fully earned.** A capability
with 20 clean runs still does not promote unless an approver is named, and
the approval is written as its own event before the `rung.change`. This felt
like ceremony until the demotion leg: demotion is automatic and approver
`null`, and the asymmetry is the point. Earning more authority requires a
human to sign; losing it requires only a failure. A ladder that promoted
itself would be the exact theatre `docs/CONCEPT.md` warns about.

**The earned rung is computed but not yet consulted.** The orchestrator
derives that `repo.write` reached autonomous, but the broker's gate still
reads the static rung from the policy when it evaluates a call. So this slice
proves the ladder moves and is auditable, but the movement does not yet
change what a call is allowed to do. That wire is a named gap, not an
oversight, and it is the first thing slice 07's durable state makes safe to
add.

## 6. What is still a guide

- **The earned rung does not gate calls yet.** `Orchestrator::step` derives
  the rung, but `BrokerRun::call` still reads the static capability rung from
  the policy. Wiring the derived rung into the gate needs durable state to be
  safe, so it waits for slice 07. `[UNENFORCED]` `ci/gate-uses-earned-rung`
  in `CLAUDE.md`.
- **No durable workflow or retries.** A step is one CLI invocation. There is
  no workflow that survives a crash between steps, no retry policy, and no
  blocking gate that pauses for an out-of-band approval and resumes. The
  approval here is synchronous: the approver identity is passed on the same
  invocation. A real OIDC approval that arrives later is slice 07 territory.
- **Human overrides and policy denials are declared demotion triggers but
  unexercised.** The budget lists `human.override` and `policy.deny` as
  demotion triggers; this slice only drives `sensor.fail`. The other two
  paths are replay code with no proof behind them yet.
- **`capability.run` is a new event kind.** Added to `docs/EVENT-SCHEMA.md`.
  It carries the rung in force and the outcome, and it is the unit the trust
  budget counts. No `policy_version`-style compatibility concern, since the
  ledger is append-only and no prior ledger used the kind.

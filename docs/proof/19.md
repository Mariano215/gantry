# Proof 19, two levels that credit a control running

## 1. The claim

Four controls landed in slices 14 to 18 and nothing scored any of them.
`config/scoring.json` had no level 4 for primitive 07 at all, and primitive 12
stopped at 3. Proof 14 said so in its own conformance delta and deliberately
left the rule to a separate piece of work, because proof 13 records what
happens when a scoring rule is written in the same breath as the feature it
scores.

Two rules are added here:

- **Primitive 07 level 4.** `docs/PRIMITIVES.md` says orchestration is strong
  with "a defined lifecycle with human gates at irreversible steps". That runs:
  `vcs.publish` is irreversible at rung `led`, so the policy holds the call
  before it executes, and `gantry approve` puts a human's answer on the record.
  The level requires a `policy.decision` reading `hold` and an `approval`
  carrying a `call_hash`.
- **Primitive 12 level 4.** The declaration is checked against the running
  system rather than assumed: `gantry drift` walks `profile_requirements` and
  appends one `drift.report` per field per run, and every `run.open` records
  the requirements this machine could not provide. The level requires a
  `drift.report` and a `run.open` carrying `unavailable`.

Neither predicate names an outcome. That is the whole substance of this proof,
and section 2 is what makes it a claim rather than an assertion.

Three of the five candidates were declined. Section 5 says why, because a
weak control credited at a strong level is worse than no rule, and this
project's self-score is its most load-bearing claim.

## 2. The attack

Executed by `docs/proof/19-run.sh` against real ledgers and the real binary.
The shape is `docs/proof/13-run.sh`, because proof 13's defect is the one these
rules are most likely to repeat.

1. Approve a held call. Primitive 07 must reach 4.
2. Refuse a held call. Primitive 07 must reach the same 4. A refusal is the
   gate working, and a rule that paid more for a yes would reward approving
   everything.
3. Hold a call and answer nothing. Primitive 07 must score 3: the gate fired
   and no human answered, which is the state the level exists to distinguish.
4. Walk the tracked profile requirements, which come back clean. Primitive 12
   must reach 4.
5. Walk a policy declaring an instruction pack hash the running system does not
   have. The walk must exit non-zero and primitive 12 must reach the same 4.
6. Never walk. Primitive 12 must score 3.
7. Assert 1 equals 2 and 4 equals 5, and that 3 and 6 are lower. Without that
   assertion the two rules are untested against the thing that went wrong last
   time.
8. Invert each rule on purpose so a broken control scores higher than a working
   one, and show `ci/scoring-outcome-neutral` and `tests/scoring.rs` go red.

Reproduce with:

```
cargo build
zsh docs/proof/19-run.sh
```

## 4. What surprised you

**The obvious predicate for the human gate was `approval.use`, and it is the
inversion.** `approval.use` is written only when a grant releases a call, so it
exists on the approve path and not on the deny path. Requiring it would have
scored a harness whose approvers said no lower than one whose approvers said
yes, which is proof 13's defect wearing better clothes: instead of paying for a
broken check, it pays for a permissive human. The event that proves the gate
ran is the `approval` itself, which `gantry approve` writes for both verdicts,
and which proof 14 was careful to make an event rather than an absence.

**Trap two fired on the first run, and it fired for real.** The first version
of the level required `{"kind": "approval"}` with no pointer. The three ledgers
scored 4, 4 and 4, and the run script failed on the negative control rather
than on the equality:

```
nobody looked: primitive 7 score 4
FAIL: a held call nobody answered scored as high as one a human answered, so the level credits nothing
```

`src/trust.rs` emits an `approval` before every earned promotion, so a rung
promotion writes the same event kind as a call approval. Level 3 of primitive
07 already requires a promotion under a named approver, so the predicate was
satisfied by the evidence for the level below it and level 4 collapsed into
level 3 for every ledger that reached it. The fix is a pointer rather than a
schema change: a call approval carries `call_hash` and a promotion approval
carries `decided`, so `{"pointer": "/call_hash", "present": true}` names the
one without naming its verdict. Two predicates in a `requires` list match
independently across the whole event set, which is the documented shape, and
the failure mode is not that the two match different events. It is that one of
them matches an event nobody was thinking about.

**The predicate schema did not need to change.** The temptation was to add a
way to say "this event and that property on the same event", and neither rule
needed it once the events were read rather than imagined. `Pred` is unchanged,
so every existing rule keeps its meaning by construction.

**A dead rule and a working rule look identical until the self-audit runs the
control.** Both rules landed inert: `docs/proof/08-run.sh` never held a call
and never walked the requirements, so the first run after adding them reported
07 at 3 and 12 at 3, exactly as before. This is the second thing proof 13
records, and it is not a lesson that transfers by reading it. The script now
performs a held-and-approved call and a drift walk, and the numbers move.

## 5. What was declined, and why

Three of the five candidates earn nothing, and saying so is the point of the
section.

**Attestation (primitives 11 and 12): declined.** Every event a real run writes
is signed, and `gantry ledger verify` reports each one verified against
`config/actor-keys.json`. The scorer cannot see that. An attestation lives on
the envelope rather than the subject, so crediting it would need a `Pred` that
points into the envelope, and even with that change the only visible fact is
that a signature is present under some key id. The ledger carries no evidence
of whose key it is: `seed_published` lives in the key registry, which is
configuration, and a scorer that reads configuration is the thing
`src/scorer.rs` exists not to be. So the rule would give a laptop signing under
a fixture seed this repository publishes the same level 4 as an HSM-backed
deployment, which is precisely the defect proof 11 fixed in the console when it
made a published-seed signature render as `verified (fixture)`. Rejected on the
rubric too: level 4 is "violations are caught mechanically", and under a
published seed the signature adds nothing to the hash chain that is already
there at level 3, because anyone holding the checkout can re-sign.

**Anchoring (primitive 11): declined.** `gantry ledger anchor` writes the
current signed head outside the ledger directory and appends a `ledger.anchor`
naming the destination. The payload carries its own `does_not_prove` string,
and the reason is that a copy is worth exactly the independence of where it was
put. A file copy written by the same process that writes the ledger, to a path
on the same disk, is not independent of the writer it is supposed to catch.
Crediting a level for it would score the shape of a control rather than a
control. CLAUDE.md already carries `[UNENFORCED] ci/anchor-schedule` for the
half that is missing, and the honest position is that the rule waits for an
anchor kind whose destination the writer cannot reach.

**Profile availability as its own level: declined, and folded into primitive 12
level 4 instead.** `run.open` carries `unavailable`, a list that is empty when
the machine provided everything and never absent, so a predicate on its
presence credits the check having run without paying for the shortfall. That
part is sound. What it does not earn is a level of its own: primitive 05 has no
level 5 that fits (level 5 is compounding, and an availability check does not
feed failures back into the harness), and a second level 4 on primitive 12
would be two names for one number. It is the second predicate on primitive 12
level 4 instead, where it belongs, because it and the drift walk are halves of
one claim: a declared value is checked against the running system, at run open
and per field per run. A rule crediting a machine for what it *cannot* provide
would have been the same inversion in a third costume, and the predicate
deliberately does not read the list's contents.

## 6. Conformance delta

Primitive 07 (Orchestration): 3 to 4. Was capped because
`config/scoring.json` had no level 4, which proof 14 recorded rather than
fixed. Now reachable, evidenced by a `policy.decision` reading `hold` and an
`approval` carrying a call hash, and exercised by `docs/proof/08-run.sh`, which
holds a `vcs.publish` call and approves it.

Primitive 12 (Governance): 3 to 4. Now reachable from the drift walk having
run and run open having recorded what the machine could not provide, exercised
by the same script. This is a per-ledger score: a ledger where drift never ran
reports 3, and one where it ran reports 4 whether every field matched or every
field diverged.

Overall level: unchanged at 3. It is the minimum across the twelve, and six
primitives still sit at 3. The self-score moving on two primitives without
moving the overall is the arithmetic working, and it is what proof 14 said
would happen when this rule was eventually written.

`rules_version` moves from `scoring-2` to `scoring-3`, because a score is
re-derivable only if the version names the rules that produced it, and two
different rule sets sharing a name would make that false.
`templates/laptop/config/scoring.json` carries the same file, and
`tests/scoring.rs` now fails if the two copies drift.

`README.md` carries the live output of `zsh docs/proof/08-run.sh`, per-primitive
4, 3, 3, 4, 4, 3, 4, 3, 3, 4, 3, 4 at overall 3, with 164 events scored.

## 7. What is still a guide

- **A hold and its answer are two predicates, not one fact.** The level is
  satisfied by a ledger with some held call and some answered call, and nothing
  requires them to be the same call. Saying that would need `Pred` to express a
  join across events, which is a larger change than a same-event constraint,
  and no rule has needed it yet. The practical consequence is small (a ledger
  with a held call and an unrelated approval scores 4) and the alternative was
  to invent schema for one rule.
- **The level does not distinguish self-approval.** On the laptop profile the
  caller can approve their own call, `approval.use` records `self_approved`,
  and the scorer ignores it. A four-eyes deployment sets `approver: named`, and
  scoring that difference would mean reading the trust budget, which is
  configuration.
- **Nothing schedules the controls the levels credit.** A harness that walks
  its requirements once and never again scores the same as one that walks them
  every run, because the ledger records that the walk ran and not how often.
  Placement and schedule are the same gap `[UNENFORCED] ci/sensor-placement-honoured`
  names for sensors.
- **`src/drift.rs` tells the operator that an unobservable field "caps
  primitive 12 at 3".** That was true until this slice and is not any more:
  an unobservable field is a reported gap, and the level credits the walk. The
  message is in a file this work does not own and is named for the lead in the
  handover rather than edited here.

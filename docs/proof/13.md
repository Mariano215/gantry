# Proof 13, instruction lifecycle telemetry

## 1. The claim

Primitive 1 was capped at 3 because `instructions/pack.md` was pinned by
hash on every `run.open` but nothing recorded whether a change to it had
been reviewed: version pinning proves what ran, not that anyone looked at
it. The `instruction-lifecycle` sensor closes that gap: it fails when the
pack's hash is not in `config/instruction-reviews.jsonl`, its verdict is a
ledger event either way, and `config/scoring.json` credits level 4 from the
sensor having run.

The rule names the sensor and not its outcome, and that distinction is the
substance of this proof. The first version of it credited level 4 from the
sensor's failure message. That inverted the incentive: a repository whose
pack was properly reviewed scored 3, and one carrying an unreviewed change
scored 4, so the way to raise the number was to break the review. It was
caught at integration by re-running the self-audit and noticing primitive 1
had not moved, because the self-audit gates a pack that passes. What earns
the level is that the lifecycle control ran. A ledger where it never ran
scores 3.

## 2. The attack

Executed by `docs/proof/13-run.sh` against the tracked sensor
`templates/laptop/config/sensors/instruction-lifecycle.json`.

1. Negative control for the scoring rule: a run that never gates its pack.
   Primitive 1 must stay at 3, because version pinning without a lifecycle
   control is exactly the state the cap described.
2. Gate the sensor against a working copy of the real
   `instructions/pack.md`, whose hash is already in
   `config/instruction-reviews.jsonl`. Must pass, and primitive 1 must reach
   4: the control ran.
3. Change the pack (append a line to the working copy) without touching the
   review record. Must fail, naming the fix, must block, and primitive 1
   must read 4 again.
4. Assert 2 and 3 scored the same. A rule that scored the failure higher
   would pay for breakage, which is the defect this proof exists to close.
5. Confirm the sensor is live: it must reject its own negative control
   (unreviewed placeholder content), or its verdicts would be worthless.

Reproduce with:

```
cargo build
zsh docs/proof/13-run.sh
```

## 4. What surprised you

The scorer's predicate schema (`Pred` in `src/scorer.rs`) is one event kind
plus a single JSON-pointer/equals pair, and each predicate in a level's
`requires` list is matched independently against the event set, so two
predicates can be satisfied by two unrelated events. Wanting to say "this
sensor AND this outcome" on one event, the first attempt matched `/message`
against the sensor's exact fix text, which is set if and only if the verdict
is a fail. It worked as a matching trick and was wrong as a rule: it made a
failing control score higher than a passing one.

The correction is smaller than the trick. `sensor.verdict` already carries
`/sensor`, so `{"kind": "sensor.verdict", "pointer": "/sensor", "equals":
"instruction-lifecycle"}` names the control in one predicate without naming
its outcome, which is what the level was always supposed to mean. The
lesson generalises: when a scoring predicate is hard to express, check
whether the difficulty is the schema or the claim. Here it was the claim.

A second thing surprised us, and it is the reason the error was caught.
Adding the scoring rule did not move the self-score, because
`docs/proof/08-run.sh` never gated the instruction pack. The scorer was
right and the rule was wrong, and the only reason anyone noticed is that the
self-audit is run rather than asserted.

The sensor's `check` command reads `config/instruction-reviews.jsonl` by a
path relative to the process's working directory, not relative to the
staged `{target}` file. The sandbox denies writes outside its own workdir
but allows reads everywhere (`src/sandbox.rs`, `(allow default)` minus the
write and network denials), so this works, but it means the sensor is only
correct when gantry runs from the repository root, exactly like every other
sensor and CLI subcommand that reads `config/policy.json` or
`instructions/pack.md` by a bare relative path.

## 5. Conformance delta

Primitive 1 (Instruction): moves from a hard cap at 3 ("instruction pack
version-pinned; no lifecycle telemetry") to reachable level 4 ("the
instruction-lifecycle sensor gated the pack"), evidenced by
`config/scoring.json` and exercised in `docs/proof/13-run.sh`. This is a
per-ledger score: a ledger where the sensor never ran reports 3, and one
where it ran reports 4 whether the gate passed or blocked. The passing and
failing cases scoring identically is asserted by the run script, because a
rule that scored them differently would pay for breakage. The self-score in
`README.md` moves to 4 because `docs/proof/08-run.sh` now gates the real
pack; before that change the self-audit claimed a lifecycle control it never
exercised. `tests/scoring.rs`
(`every_scoring_predicate_kind_is_a_documented_event_kind`) already passes
because `sensor.verdict` was documented in `docs/EVENT-SCHEMA.md` before
this slice (primitive 10 uses the same kind). Overall level unaffected: it
is the minimum across primitives, and this slice only raises a ceiling on
one of them.

## 6. What is still a guide

`config/instruction-reviews.jsonl` is appended to by hand: nothing in this
slice enforces that a human (or an agent under a named actor) actually
reviewed the content before adding a line, only that a line with the
matching hash exists. A reviewer could append the current hash without
reading the diff, and the sensor would report clean. Catching that would
need the review record to carry an attestation the ledger's actor-key
registry verifies (`config/actor-keys.json`, already used for ledger
attestations since the post-nine gap work) rather than a plain JSON line,
which is future work, not marked `[UNENFORCED]` in CLAUDE.md because
CLAUDE.md makes no claim about review authenticity, only about lifecycle
telemetry existing, which this slice enforces.

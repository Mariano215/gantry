# Proof 15, drift reads what it can and admits what it cannot

## 1. The claim

`docs/POLICY-SCHEMA.md` has described `gantry drift` since slice 00. There was
no such subcommand. Nothing emitted `drift.report`. `observed_by` was required
on every profile requirement and two of the nine were ever compared, both
inside `src/gateway.rs` as a side effect of pinning authority.

Primitive 12's own document said the policy is "a guide plus a sensor". The
sensor half was the guide describing a sensor.

The claim now is that the walk runs, that every field reports every run, and
that the answer for a source this build cannot read is `unobservable`, never
`match`. The last part is the only interesting one. Reporting a match is easy
and always available: pick any two values the code already holds and compare
them. The tracked policy makes that trap concrete. `egress.observed_by` is
`sandbox.egress_allow`, the seatbelt profile's allowlist is generated from the
policy's own `egress.allow`, and both are empty on the laptop profile. An
implementation that "observed" it would print `match` forever, on a host whose
route table permitted the world.

## 2. The attack

1. Point a field at `netns.route_table`, the source the schema itself names for
   egress, on a machine with no network namespace. It must report
   `unobservable` with no running value, not `match`, and not an error.
2. Do the same through the source the tracked policy actually carries,
   `sandbox.egress_allow`, where a naive reader has something real-looking to
   read and would agree with itself.
3. Put a typo in an `observed_by`. The field must report as a gap and the walk
   must continue: a scan that aborts on one bad line reports nothing about the
   fields it never reached, which is silence that looks like health.
4. Declare a value the running system does not have. Both values must be
   named, the fix must name the change to make, and the command must exit
   non-zero.
5. Run the walk twice. The second run must report every field again, including
   the matches, or the ledger cannot tell a clean scan from a stopped one.
6. Break the check in CI, twice, in the two ways it is supposed to catch: make
   an unreadable source return a value, and make a divergence exit 0 while
   still printing the divergence.

Attacks 1 to 3 and 5 are also in `tests/drift.rs`. What follows was run.

**Attack 2, the trap in the shape the tracked policy carries.** Line two.
`egress` declares `allowlist` and the allow list is `[]`. The sandbox this host
would build has an empty allowlist too, so an implementation reading it back
gets agreement and prints `match`. The report says `unobservable` and names the
circularity as the cause. This is the one line of this document that had to be
right.

**Attack 4, a real divergence, found on the first run.** The tracked
`config/policy.json` declares a host permission hash of `sha256:5388e503...`
and `.claude/settings.json` hashes to `sha256:5a22b9dd...`. The file is not
edited: `git show HEAD:.claude/settings.json | shasum -a 256` gives the same
`5a22b9dd...`, so the settings file matches version control and the policy's
declaration is what is stale. Nothing in the project reported this before this
slice, because `settings_divergence` compares the file against git and the
declared hash in the policy had no reader. That is the whole thesis in one
field.

## 4. What surprised you

**Deciding which sources are real took longer than reading them.** The code for
six observations is about eighty lines. Working out that two of the nine
declared sources are not observations at all, and that one more is weaker than
it looks, was the work. The table in `docs/POLICY-SCHEMA.md` now says which is
which, because a reader of a green scan deserves to know that four of the nine
fields were never checked by anything.

The weak one is `gateway.identity_source`. It is read off the newest event
already on the ledger, so it is telemetry rather than configuration, which is
the right shape. But the producer of that event is this same binary writing a
constant, so on a ledger only gantry has ever written, gantry is observing
gantry. It is honestly better than reading the policy back and it is honestly
not a query put to an identity provider. When OIDC lands, this source has to
start reading a token or it becomes the egress trap in a different field.

**The first real divergence was in the tracked policy, and nobody put it
there.** `config/policy.json` declares a `host_permissions` hash that
`.claude/settings.json` stopped having at some point before this slice. Every
existing check passed: the settings file matches git, host parity passes,
`policy check` is clean. The declared hash simply had no reader. The command
found it on its first run against the repository that wrote it.

**`authority.declared: false` could not be implemented, and should not be.**
`docs/POLICY-SCHEMA.md` asked for it in this section. `docs/EVENT-SCHEMA.md`
records that v1's `authority.declared` became the `authority.diverged` list in
slice 01, mapped to proof-00 finding (a). Two documents specified the same
control in two incompatible shapes for fourteen slices, and the policy schema
was the stale one. The list is strictly better
(it names which field diverged instead of one boolean), it already exists, and
the drift run now writes its findings into it. So the diff is one line in
`src/main.rs` extending `Pinning.diverged`, `src/gateway.rs` is untouched, and
the schema section that asked for the boolean now says why there is not one.

**The exit code wants to say two different things.** A divergence is a
failure, a gap is not, and both are things the scan found. Exiting non-zero on
a gap would make `gantry drift` permanently red on the tracked policy, which
would get it switched off within a week, which is how a real sensor dies. Exit
1 means divergence; gaps are counted and printed and named in the summary. The
CI check reads the gaps out of the text and the divergence out of the status,
which is why it needed both.

## 5. Conformance delta

**No score moves, and the reason is arithmetic rather than modesty.**
`config/scoring.json`'s primitive 12 rules credit a named `policy.decision`
deny at level 3, and nothing in them mentions `drift.report`. A rule that
credited the new event is deliberately not part of this work, for the reason
proof 13 records: a scoring rule written in the same breath as the feature it
scores pays for the wrong thing and nobody notices, because the number moves
either way. A level 4 for primitive 12 has to name the control running, which
here means a `drift.report` with outcome `match` for a source that was actually
read, and `docs/proof/08-run.sh` has to exercise a drift walk, or the rule
lands and the number does not move.

What did change is what the rubric measures. `docs/PRIMITIVES.md` puts a
declaration nothing checks at maturity 3 by construction. Five of nine profile
requirements are now checked against the running system on every push, and the
four that are not say so in the report rather than passing quietly. The overall
level stays where it was; the distance between what the document claims and
what runs got shorter by four fields.

## 6. What is still a guide

- **The egress allowlist is unchecked.** Both declared sources for it
  (`netns.route_table` in the schema, `sandbox.egress_allow` in the tracked
  policy) are admissions. Making it an observation needs a reader for the host
  packet filter, or a Linux network namespace to read a route table out of.
  This is the largest remaining hole in primitive 12 and it is now visible on
  every run instead of implied by silence.
- **One value per field is compared.** `egress.allow`, `ledger.anchoring`,
  `ledger.key_custody` and `identity.fallback_permitted` sit next to compared
  values and nothing reads them. `ledger: match` means a signed head exists,
  not that anchoring is `none` because nothing anchors.
- **Nothing inside the binary schedules the walk.** "On a schedule" is CI: the
  gate on every push and the weekly cron already in
  `.github/workflows/ci.yml`. A harness installed from the template gets the
  subcommand and no schedule, and that is a gap the template would have to
  close with a cron of its own.
- **`gantry drift` reads `instructions/pack.md` and `.claude/settings.json`
  relative to the working directory,** like every other subcommand, so drifting
  a harness elsewhere means running from it. Same constraint as the broker and
  `gantry approve`; not new here.
- **A gap does not cost anything.** An unobservable field is reported, counted
  and appended to the ledger, and no rung comes down and no gate tightens
  because of it. Whether a control nothing checks should cost a capability
  autonomy is a real question and it belongs with the trust budget, not here.

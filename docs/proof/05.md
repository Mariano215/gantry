# Proof 05, sensor bus

## 1. The claim

A sensor is a check with a lifecycle placement whose verdict names the fix;
a blocking failure blocks the result and the agent corrects on rerun with no
human in the loop, both attempts recorded; and a sensor that passes its own
negative control is reported as broken, never as a clean pass, so a board of
green-but-dead sensors cannot happen.

## 2. The attack

Executed by `docs/proof/05-run.sh`, `tests/sensor.rs` and `src/sensor.rs`.
The repair turn uses the local ollama model in `config/providers.json`.

1. A findings document with an embedded private key is put through the
   `no-private-key` sensor (`docs/proof/fixtures/no-private-key.json`,
   placement `pre_integration`, blocking). The sensor must fail, block, and
   its verdict must carry the fix. Then, with no human editing the file, the
   model is handed the artifact and the fix message, its output replaces the
   artifact, and the sensor reruns and must pass. Both verdicts on one
   ledger.
2. A sensor that cannot fail: `broken-sensor.json`, whose check is `true`
   and ignores the target. It must be reported `broken`, and the run sealed
   `sealed-with-broken-sensor`, not clean.
3. Added after the slice, when the `no-private-key` check was widened: key
   material this project would actually leak but the one-header check never
   saw (a raw hex ed25519 seed, an OpenSSH block, an RSA or EC header), a
   document of this system's own sha256 hashes that must still pass, and the
   two ways a widened check goes wrong. One control per branch, and the check
   is only trusted if it rejects all of them and accepts the telemetry.

The mechanism is pinned by the suite: `tests/sensor.rs` drives the
block-then-correct arc and the broken-sensor case with a scripted correction
(no model, so the test is offline and deterministic); `src/sensor.rs` unit
tests pin the verdict logic, the liveness check, and the load-time refusal
of a sensor whose fix is empty or whose check never reads the target.

Reproduce with:

```
cargo build
zsh docs/proof/05-run.sh
```

## 3. What happened

Workdir `/tmp/gantry-proof05.jWW8YE`. All output verbatim.

Attack 1, the block-then-correct arc. The sensor failed, blocked, and named
the fix; the model repaired the document; the rerun passed:

```
[attempt 1] sensor no-private-key -> fail (blocked: true)
    Remove the embedded private key block from the document. Keep the finding text, but replace the key material with the words: [redacted, referenced by broker handle].
[bus] blocking failure; asking the model to repair the artifact
[attempt 2, after repair] sensor no-private-key -> pass (blocked: false)
sealed at ledger size 4

the private key block is gone from the repaired artifact
```

Both verdicts on one ledger, and the seal records the arc rather than only
its clean end:

```
{"sensor":"no-private-key","verdict":"fail","blocked":true}
{"sensor":"no-private-key","verdict":"pass","blocked":false}
{"outcome":"sealed-with-blocking-failure","blocked_any":true,"broken_any":false}

```

Attack 2, the sensor that cannot fail:

```
[attempt 1] sensor always-green -> broken (blocked: true)
    Sensor always-green passed its own negative control, so it cannot fail and its verdicts are worthless. Fix the check so the negative control fails, then re-register.
the always-green sensor is reported broken, not clean
{"outcome":"sealed-with-broken-sensor","broken_any":true}
entries: 3
```

Both ledgers verify. The suite stands at 77 tests plus clippy with
`-D warnings`, all clean.

Attack 3, the widening. The check the slice shipped with was
`! grep -q 'BEGIN PRIVATE KEY' {target}`: one PEM header and nothing else. A
raw hex ed25519 seed, which is exactly how this project stores its own actor
key in `config/actor-key-fixture.seed`, passed it clean, and so did an
OpenSSH block and an RSA or EC header. The check is now:

```
! grep -Eq '(-----BEGIN [A-Z0-9 ]*PRIVATE KEY|^[[:space:]]*[0-9a-f]{64,}[[:space:]]*$)' {target} && ! grep -Eqi '(seed|secret|private)[^0-9a-f]{0,24}[0-9a-f]{64}' {target}
```

Three branches: any PEM or OpenSSH private key header, a line holding nothing
but 64 or more hex characters, and 64 hex characters on a line that also
carries the word seed, secret or private. Run against a findings document
carrying a bare seed, then one carrying an OpenSSH block:

```
-- a raw ed25519 seed, the shape this project's own key is stored in --
[attempt 1] sensor no-private-key -> fail (blocked: true)
    Remove the key material from the document. Keep the finding text and put the words [redacted, referenced by broker handle] where the key was. ...
exit=1
-- an openssh private key block, which the old check never saw --
[attempt 1] sensor no-private-key -> fail (blocked: true)
exit=1
-- the same sensor on a document of this system's own hashes --
[attempt 1] sensor no-private-key -> pass (blocked: false)
```

The third line is the one that matters. A sensor that fires on the hashes its
own control plane prints gets switched off, and a switched-off sensor is
worth less than a narrow one. So the sensor now declares controls in both
directions: six negative controls, one per kind of key material, and two
positive controls taken verbatim from `config/policy.json`,
`config/instruction-reviews.jsonl` and a real `run.open` envelope. Liveness is
all of them, and the mechanism is what catches both ways of getting the
widening wrong. The pre-widening check, declared against the widened
controls, and then the naive widening ("64 hex characters is a secret"):

```
-- the pre-widening check, declared against the widened controls --
[attempt 1] sensor narrow-key-check -> broken (blocked: true)
    Sensor narrow-key-check passed negative control 2 of 6, so that branch of its check cannot fail and its verdicts are worthless. Widen the check until control 2 fails, then re-register.
exit=1
-- the naive widening, 64 hex characters is a secret --
[attempt 1] sensor hex-is-a-secret -> broken (blocked: true)
    Sensor hex-is-a-secret rejected positive control 1 of 2, so it fires on content it is required to accept and will be switched off, which is worse than a narrow check. Narrow the check until control 1 passes, then re-register.
exit=1
```

Control 2 is the OpenSSH block: `grep 'BEGIN PRIVATE KEY'` never matches
`BEGIN OPENSSH PRIVATE KEY`, so the old check is reported broken rather than
clean the moment it is asked to carry the wider claim. That is the point of
the multi-control change. A sensor with one control and a check that catches
four kinds of thing reports live while three quarters of it is dead.

The whole suite stands at 136 tests, `zsh ci/run.sh` ends in `ci gate
passed`, and the liveness sweep runs every control on every push:

```
-- the liveness sweep over the tracked sensors --
sensor instruction-lifecycle is live: it rejects its negative control
sensor no-private-key is live: it rejects its negative control
```

## 4. What surprised me

**The liveness check is a sensor running its own sensor, and that recursion
stops in exactly one place.** `no-private-key` proves it can fail by
rejecting its negative control; `always-green` fails that meta-check. But the
meta-check itself is just "the negative control does not pass", a
computational predicate that could in principle also be broken. It is not,
because it is not a declared sensor but a fixed property of the bus: liveness
is the one check the bus does not let you define, which is what keeps the
regress one level deep. Writing this slice made clear why the rubric puts
"the sensor that guards the sensors" outside the sensor abstraction.

**The tiny local model repaired the document cleanly on the first try.** The
same `qwen3:0.6b` that complied with a prompt injection in proof 04 here did
the useful version of "follow the instruction in the text": it removed the
key block and kept the findings. The sensor, not the model, is what
certified the repair, so a worse model would have produced a second failing
verdict and a non-clean seal rather than a false pass. The autonomy is safe
because the gate is computational and the model's output is untrusted until
it passes it.

**The false-positive direction is the sensor's real failure mode, and
nothing was checking it.** A private key and a sha256 hash are both 32 random
bytes; no rule can tell a raw seed from a content hash by looking at the
bytes. The rule has to be contextual, so the one chosen is: hex is key
material when it is alone on its line, or when the line labels it seed,
secret or private. Every hash this project emits carries context on its line,
a `sha256:` prefix, a JSON key, a `payloads/` path or surrounding prose, so
none of them trip it. That was verified against the tracked files rather than
assumed: `config/policy.json`, `config/instruction-reviews.jsonl`,
`config/actor-keys.json`, `config/skill-keys.json`, `README.md`, `CLAUDE.md`
and a live ledger all pass, and only `config/actor-key-fixture.seed` and
`docs/proof/fixtures/skill-repo-audit.pub` fire. The first is a true
positive. The second is the boundary being honest: a 32-byte public key on a
bare line is byte-for-byte indistinguishable from a seed, so the check calls
it key material. Accepted, because this sensor gates findings documents,
where a bare hex line is far likelier to be a leaked key than a pasted hash.

**Positive controls exist because of that, not for symmetry.** Before this
change the bus only ever asked "can this sensor fail". A widened check can
also fail by firing on everything, and the operator response to that is to
switch it off, which is a worse outcome than the narrow check it replaced.
So a sensor now also declares content it must accept, checked in the same
place and on the same schedule, and the naive widening above is reported
broken by it. The negative control keeps the sensor from being useless; the
positive control keeps it from being unbearable.

**Placement is recorded but not yet enforced.** A sensor declares
`pre_integration`, `post_integration` or `continuous`, and the verdict
carries it, but nothing in this slice makes a `pre_integration` sensor
actually run before an integration step, because there is no integration
step until the orchestrator. The field is honest metadata that the next
slice consumes; stated here so it is not mistaken for a running control.

The widening in attack 3 does not move primitive 10. It grows what one
sensor covers and makes the liveness guarantee hold per branch instead of
per sensor, which closes a hole in the existing mechanism rather than adding
a new one. Placement is still metadata, so 4 stands.

## 6. What is still a guide

- **Placement is metadata, not a schedule.** `pre_integration`,
  `post_integration` and `continuous` are recorded on every verdict but
  nothing runs a sensor at its placement, because the lifecycle that would
  call it is the orchestrator's (slice 06). `[UNENFORCED]`
  `ci/sensor-placement-honoured`.
- **Liveness is swept on a schedule now, not only at use.** This item used to
  name `ci/sensor-liveness-schedule` as an open gap. `gantry sensor live`
  runs every tracked sensor's controls standalone, `ci/run.sh` runs the sweep
  on every push, and the workflow adds a weekly cron, so a sensor that rots
  between pushes is caught by the schedule rather than by the next unlucky
  verdict. What is still true is the window: a sensor that rots the hour
  after a push is live in the record until the next push or the next cron.
- **Inferential sensors are a declared kind with no distinct runner.** The
  `SensorKind::Inferential` variant exists and is recorded, but every sensor
  in this slice is computational. A model-judged sensor with its own
  liveness story (a negative control the judge must reject) arrives when the
  workload needs one.
- **What the widened key check still misses.** A bare seed pasted
  mid-sentence with no label ("the key is 7c93e0a5..." on a line with other
  words) reads exactly like a hash and passes. So does base64 key material
  with the PEM header stripped, a seed split across lines, and any hex run
  that is not 64 or more characters. The `fix` message says so, because a
  pass from this sensor is not a statement that a document is clean, only
  that it does not carry key material in the shapes named. Closing the
  mid-sentence case needs entropy scoring or a labelled-hash convention, and
  either is a bigger change than the leak it prevents is worth today.
- **The repair loop is one turn and lives in the CLI.** `gantry sensor
  repair` does exactly one model turn on a blocking failure. A bounded
  retry loop with escalation is the orchestrator's job, not the bus's.

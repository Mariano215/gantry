# Proof 21, a trace view that draws only the edges the record carries

## 1. The claim

The console draws the ledger as swimlanes on a clock, one lane per actor that
wrote an event, and an arrow only where a producer recorded a peer. It holds no
table mapping an event kind to a source and a destination lane, so a handoff
nothing observed is never drawn as one. The picture is sparse, and the
sparseness is the finding.

Three producer and API changes came first, because the view needed correlation
the record did not carry:

- `policy.decision` carries `request_id` and `call_hash`.
- The approvals inbox, and `gantry approve`, join on those instead of pairing a
  decision with whatever `tool.request` came before it.
- `/api/verify` returns the `seq_gaps` it has computed since slice 18 and
  discarded ever since.

Twelve commits, `24f970d` through `d704ebb`, on `slice-21-trace-view`.

## 2. The attack

Two questions, and the second is the one that mattered.

First: can the view be made to draw an edge the record does not support? The
structural answer is in `tests/invariants.rs`
(`the_trace_view_derives_no_edge_from_an_event_kind_alone`), which reads
`assets/trace.js`, extracts the `PEER_FIELD` literal and fails if any entry
resolves a peer without reading a subject field. The legend prints
`inferred: 0` beside the observed count, so the page states what it refused to
draw and not only what it drew.

Second: does every assertion added in this slice actually die when the thing it
names is removed? Each was broken deliberately, one at a time, and reverted.
Four did not die, and finding that is most of what this document records.

## 3. What happened

### 3.1 The assertions that died as intended

| Break | What the gate said |
|---|---|
| `actorId(ev.actor)` to `ev.actorr` | `the trace view rendered without "agent:gantry-broker"` |
| `s.tool` in `PEER_FIELD` to `s.toool` | `the trace view rendered without "tool:Bash"` |
| `matches` returning `true` unconditionally | `the tracefiltered view rendered "tool.request", which is an event the filter excludes` |
| `s.call_hash` in the span derivation | `the trace view rendered without "held "` |
| `seq_gaps` to `seqGaps` in the verify handler | `the trace view rendered without "2 events missing"` |
| `_attestation_state` to `_attestation_statee` | `the trace view rendered without "class="warn-text mono">1<"` |
| `detailPane` deleted from the render | `the tracedetail view rendered without "class="trace-aside""` |
| clustering removed, one mark per event | `the trace view rendered "38 marks for 38 events"` |

### 3.2 The assertions that did not die

**The unattested column.** The first check written for the per-lane attestation
count asserted the word `unattested` appeared in the DOM. That is a column
header. The attestation state was read under a wrong name and the gate stayed
green.

The replacement was wrong too, in a more interesting way. It assumed every
event on the fixture verifies, so "no lane raises an unattested count" would be
the healthy state. Five of the fixture's events carry no attestation at all,
because `gantry approve` and `gantry ledger append` do not sign, so the healthy
state already lights that column. The check now takes the number off the ledger
for the lane that has some but not all of its events unattested, refutes that
lane's whole event count, which is what the broken read produces, and refuses
to run if the fixture stops containing such a lane.

**Both detail pane checks.** `expect tracedetail "$EVENT_ID"` and
`expect tracedetail "from first,"` were both written believing they tested the
pane. Every mark carries `data-event="<id>"` and a title reading
`... from first, ...`, both added in the same commit as the pane, so both
assertions passed with `detailPane` deleted from the render. They now assert
the pane's own class, the split layout, and a field only the detail tree
prints.

**The lane loop and two panel subtitles.** The loop over actor ids asserted
nothing at all if its `jq` returned empty, silently, and in zsh a `for` over an
empty list runs zero iterations without complaint. `expect trace "lanes,"` and
`expect tracefiltered "drawn"` matched panel subtitles that render with zero of
everything. All three now compare numbers computed off the ledger, and the lane
loop refuses to run below two lanes.

### 3.3 What a review found that the breaks did not

A read-only review of the branch found the half of the correlation fix that was
missing. Slice task 2 was scoped to `src/console.rs` and never mentioned
`gantry approve`, so the slice was about to ship a console that reads
correctly and a CLI that writes wrongly.

`src/main.rs` still paired each decision with the `tool.request` immediately
before it. Driven by a test that interleaves two calls (request A, request B,
then the decision that held A):

- `gantry approve <A>` exits with `no request run-9000-req-A on the ledger`.
  That is false, and it is the exact command the inbox prints under the hold.
- `gantry approve <B>` writes a grant carrying `call_hash sha256:bbb` under A's
  rule, a grant for a call nothing ever held. The broker binds a grant by call
  hash, so it would release B on an approval nobody gave for B.

Recorded as `approve_binds_the_grant_to_the_call_the_decision_named` in
`tests/broker.rs`, which failed on both halves before the fix.

Both readers also took the adjacency fallback with `or_else`, which
short-circuits, so on a ledger holding events from both sides of the upgrade a
later fieldless decision could consume a request from many events back. That is
the defect `d8ddf3d` claimed to close. Both now take the fallback
unconditionally.

The same review found three filter defects. `att` matched on substring, and
`"unverified".includes("verified")` is true, so `att:verified` drew unverified
events and `!att:verified`, the query an auditor types to find exactly those,
hid them. Truncation was announced only when a browser-side term had run, so a
plain `kind:` filter over a log larger than one page rendered
`1,000 of 1,000 drawn` and said nothing about the rest. The link labelled
"narrow the server-side read" produced an empty expression when no term could
be pushed down, which cleared the filter and drew everything.

### 3.4 The filter language said two things with one syntax

Measured against a served ledger rather than reasoned about:

```
kind:tool           0 of 0 drawn      server, whole value
kind:tool.request   4 of 4 drawn
rule:r-             4 of 33 drawn     browser, substring
!verdict:deny      32 of 33 drawn
```

`kind` and `run` are whole-value matches at the API; every browser-side term is
a substring. Same syntax, two rules, and nothing on screen said which applied.
The bar now names each term, the side that answered it and the rule it used. A
term naming a field with no browser-side reader is dropped and named rather
than matching everything, which is what `!since:` did.

The negation logic itself was correct: `!verdict:deny` keeps events carrying no
verdict at all, which is the right reading of "not a denial".

### 3.5 Marks painted over each other

Eight events inside 7ms of a 220ms run all resolved to within 3% of a track
whose marks are about 34ch wide. The lane head read `8 events` above a track
showing one. Marks resolving to the same position are now drawn as a single
mark carrying its count and the kinds it stands for, with every member named in
its title, and the legend states marks and events on every render.

The obvious break, raising the position resolution, does not disable this:
events sharing a millisecond collapse at any resolution. The refute was proved
by removing clustering outright.

## 4. What surprised you

That writing the check honestly was harder than writing the feature, three
times over. The unattested assertion took three attempts, and the second failed
against a premise about the fixture that was simply untrue.

That the correlation fix had a writer half nobody noticed, including the plan.
The reader was fixed with a test that drove the interleaving; the writer, six
feet away in `src/main.rs`, kept the old walk and the old comment asserting the
pairing could not go stale. The comment was load-bearing in the wrong
direction: it said the thing that had just been disproved.

That `verdict:deny` draws two events on the fixture and not one. The policy's
denial and the human's refusal both record that field, which is correct and was
not anticipated.

## 5. Conformance delta

Primitive 09, observability: unchanged in score. The view renders existing
telemetry and adds no producer.

Primitive 07, human gate: the approval path is materially more correct.
`gantry approve` could bind a grant to a call the record never held, and a
grant is what releases a call at the chokepoint.

Primitive 12, governance: `seq_gaps` reaches an operator surface for the first
time. The report existed since slice 18 and no console could show it.

The static scan on this repository is unchanged at overall 0 against
telemetry's 3, and still reports 4 unenforced markers.

## 6. What is still a guide

- The trace reads on mount. There is no live update, and a run in flight is
  seen by reloading.
- `PEER_FIELD` covers three kinds, so every other kind is a marker and the
  picture is sparse. That is the design, and the fix for a missing arrow is a
  producer recording a peer.
- `TRACK_SLOTS` is a fixed resolution, because the track's pixel width is not
  known where the clustering happens. Clusters get coarse on a narrow window
  and nothing measures that.
- The time axis is linear, so a run with one long wait compresses everything
  else. The idle-gap squash from the design was deferred.
- `laneStats` counts `verified` as attested with no qualifier, so an event
  signed under the published fixture seed reads the same as one under a held
  key. `docs/CONSOLE-API.md` requires that distinction and this column drops
  it. The overview has the same shape, so it is not new here, and it is not
  fixed either.
- A call refused and later approved draws one span, reading `refused`. The
  second answer is not drawn.
- The `views.js` and `trace.js` import cycle is safe only because
  `eventDetail` is a function declaration and so is hoisted before either
  module evaluates.
- `.lane-stack .edges { left: 24ch }` repeats the `24ch` from the lane grid.
  Two constants that must agree or every edge draws offset from its marks.

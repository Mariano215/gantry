# Proof 20, the approval inbox, and two places the console lied

## 1. The claim

Slice 14 made a held call resolvable. `gantry approve` writes the answer, the
broker releases the retry, and a refusal is an event rather than an absence.
What it did not do was tell anybody. Proof 14 records it as the first item
under "what is still a guide": no approval inbox, so an approver finds held
calls by reading the ledger view or by grepping a ledger directory.

An approval path nobody can see is complete and useless. A run blocks, the
agent stops, and the human who could unblock it has no reason to look.

The claim now is that the console names every call waiting on a human, says
which of them nobody has answered and which somebody refused, and prints the
exact command that resolves each one. And that it still writes nothing.

Two smaller claims, both recorded as known defects in `docs/proof/11.md`, both
the same species: the screen said something the ledger did not support.

- The Run view drew at most 1000 events and said nothing about the rest.
- An expanded row collapsed when the five second poll repainted.

## 2. The attack

1. Build a ledger with held calls in every state the record can produce, and
   check that the inbox tells them apart. A console that renders "nobody
   looked" and "somebody said no" the same way loses the distinction slice 14
   exists to draw.
2. Show a grant that releases nothing (spent, or under an approver the trust
   budget does not permit) as releasing nothing. The console must gate on the
   same predicate the broker gates on, or it is guessing.
3. Rename each field the new views read, one at a time, in `src/console.rs`,
   and watch the render check go red. A render assertion never seen red is
   worthless.
4. Truncate a run and read the page. If the page looks whole, the fix failed.
5. Open a row, make the ledger grow underneath it, and read the payload after
   the poll repaints.
6. Serve a ledger with one altered event and render it. The console must
   refuse to present it, and that refusal must now be checked by the gate
   rather than by a screenshot in proof 11.

## 3. What happened

Run against real ledgers built by the binary, not reasoned about.

fourth case the CLI cannot easily produce, a grant already spent by a retry
with the call held again after it, and asserts it reads `spent` rather than
`released`. A single use grant rendered as still usable would be the worst row
on the page.

### The Run view no longer truncates in silence

`/api/events` returns at most 1000 rows and reports how many matched. To see
the truncated branch actually render, `EVENT_PAGE_MAX` in `assets/views.js`
was set to 3 by hand, the binary rebuilt, and a run of 8 events rendered:

```
events
3 of 8
drawn of the events matching this run id; 5 are not on this page

Waterfall
this waterfall is the first 3 events of 8 on this run
5 events carrying this run id are not drawn here. The API returns at most 3
events per read, in append order, so what follows is the start of the run and
not all of it.
fix: read the rest in the ledger view filtered to this run, which pages the
same events, or narrow the read with the since filter there.
```

`EVENT_PAGE_MAX` was then restored to 1000. The untruncated case says so too,
and that is what the gate asserts, because the fixture ledger is short:
`7 of 7` and "so this waterfall is the whole run".

The same read shows up on the overview, which said "over the N most recent of
M events". It was the wrong direction: limit and offset run over the log in
append order, so a truncated page is the oldest events. It now reads "over the
first N of M events in append order".

### An expanded row survives the repaint

The poll repaints only when the event set changed, and timing a real append
against a page running on Chrome's virtual clock is a race. The dev fixture
server got a `grow` mode instead: every `/api/events` answer carries one more
event than the last, so the first poll always repaints. Same page, same
deep link, same virtual time budget, once with the fix and once without:

```
$ python3 dev/serve.py healthy grow 8793
$ chrome --headless=new --virtual-time-budget=30000 --dump-dom '.../#/ledger/ev-01JQ0006ZK9F3TQW06'

without the open-row registry:  the page ended at 30 shown, 30 loaded  (24 on
                                the first read)
                                expanded detail panes: 0
with it:                        the page ended at 30 shown, 30 loaded
                                expanded detail panes: 1
```

Six repaints in both runs, and the payload is still on screen in the second.

### The gate now renders the paths it could not see

`ci/console-render.sh` rendered six views and asserted values off an
eleven-event ledger. It now builds a 37-event ledger with three held calls, one
refusal and one grant, and renders eleven pages: the seven views, a run's own
waterfall, a ledger row opened by its event id, a hold opened by its call hash,
and the takeover, served from a second console over a copy of the ledger with
one event altered.

```
$ zsh ci/console-render.sh
seven views, two deep-linked rows and the takeover rendered against a 37-event
ledger; head, score, events, events/:id, runs, policy, trust, approvals and
verify all reached the screen
```

The takeover assertions are the ones worth naming. The check asserts the
altered event's id appears in the fault table, that the offline reproduce
command is printed, and then refutes `The twelve primitives` and
`Attestation coverage`, which are the panels of the healthy overview. A
console that rendered the scorecard over a record that does not check out is
the exact failure this product exists to prevent, and until now that claim was
carried by a screenshot in proof 11.

## 4. What surprised you

**An assertion that could not fail, found by trying to make it fail.** Seven of
the eight renames turned the gate red on the first attempt.
`releases_next_call` did not. That field decides which of the two inbox tables
a hold lands in, and every string the check looked for is on the row itself:
the state tag still read `released`, the approver was still named, the rule was
still there. The row moved to the wrong table and every assertion still passed.

The fix is not another string on the row. It is the empty state of the table
that must not be empty: with the partition working, this ledger has a row in
each table, so either "no grant on this ledger releases a call right now" or
"no held call on this ledger is waiting" appearing at all is the split having
broken. That is a refutation rather than an expectation, and it is the only
thing on the page that could see the field move.

This is the project's own thesis landing on its own gate. A check that passes
is not evidence until it has been made to fail, and the one assertion never
seen red was the one that was worthless.

**Two things behind a click turned out not to need a click.** Proof 11 records
the expanded row and `/api/events/:id` as unreachable without a CDP driver, and
that driver was rejected because it needs a global `WebSocket` from a Node
version nothing pins. But the ledger view already opened a row named in the
URL, for deep links from a fault or a sample event. A route is not an
interaction. Giving the inbox the same treatment, `#/inbox/<call hash>`, made
the copyable command renderable too, and it is a better inbox for it: a held
call is the thing one person hands another, so it should have a link.

The verification takeover was the same shape. It is what the router does
*before* any view mounts, so serving a second, altered ledger reaches it with
no interaction at all. Both were reachable the whole time, and the missing idea
was not a driver, it was a URL.

**The dev fixture server earned its keep on a question the real binary cannot
answer.** Whether an expanded row survives a repaint depends on the poll seeing
a change, and a change means the ledger grew between two reads. Against the
real binary that is a race with the browser's virtual clock, and a gate that
races is a gate people learn to skip. `dev/serve.py grow` answers every read
with one more event than the last, which makes the question deterministic, and
it serves `assets/` from disk, so what it exercised is the same front end the
binary embeds. The header of that file already said it exists for states a real
ledger cannot easily produce; this is the third one.

**The read-only rule was the easiest part of the design and the one worth
stating.** An inbox with an approve button is the obvious product, and it is
wrong here for a reason that has nothing to do with the button. `gantry
approve` writes an event naming a human. On loopback with no identity story,
the console knows nobody: it would write that name because the socket was
reachable. The record would then say a person approved something when what
happened is that a browser was open. So the console prints the command and the
person runs it, and where the profile permits any approver the command carries
a placeholder rather than a name the console guessed. That last detail was not
in the original design; it fell out of writing the command generator and having
nothing truthful to put in the argument.

## 5. Conformance delta

No primitive moved, and this is the fifth proof in a row to say so.

Primitive 07 is where an approval inbox would score, and
`config/scoring.json` has no level 4 for primitive 07 at all: proof 14 records
that its levels stop at 3, so orchestration scores 3 whether or not a human can
see what is waiting for them. Adding that rule is somebody else's work with its
own adversarial case, for the reason proof 13 records: a scoring rule written in
the same breath as the feature it scores tends to pay for the wrong thing.

Nothing here writes to the ledger, so there is no new telemetry for the scorer
to read. What changed is that three claims which were true and unobservable are
now observable, and one that was false on screen is not.

The console's own gate got materially stronger, and that is not a score:
`ci/console-render.sh` went from six views to eleven pages, and now covers
`/api/approvals`, `/api/events/:id`, the truncation notice and the verification
takeover, each asserted against values read off a ledger at check time.

## 6. What is still a guide

- **The repaint check is not in the gate.** The experiment in section 3 is
  deterministic but it runs against `dev/serve.py`, and putting a dev fixture
  server in `ci/run.sh` would mean the gate no longer proved the binary serves
  what it renders. Against the real binary the same question is a race with the
  virtual clock: an append has to land between the initial read and a poll, a
  window of tens of milliseconds. A flaky gate is worse than a documented gap,
  so this one is documented. `[UNENFORCED]` `ci/console-open-row-survives-poll`
- **Anything that genuinely needs a click is still uncovered**, and after this
  slice the list is short: collapsing a row, the filter box, the kind chips,
  paging the ledger view, the theme toggle, dismissing the takeover, and the
  permanent alert bar that follows the dismissal. All of them need a real
  input event. `dev/serve.py` can drive four of these with `?drive=`, which is
  how the proof 11 screenshots were taken, but a check built on that would be
  asserting against the dev server rather than the binary. A CDP driver is
  still refused for the reason proof 11 gives: it needs a global `WebSocket`,
  which means Node 22 or newer, and nothing pins the runner's Node version.
- **The `ineffective` state cannot be reached on this profile.** A grant under
  an approver the trust budget does not permit is a real state, the broker
  re-checks for exactly it, and the laptop profile's approver is `any`, so
  nothing on this machine can produce one. It is asserted nowhere and rendered
  from the same code path as the others. A `regulated` profile with named
  approvers would exercise it.
- **Layout is still unchecked.** The render check reads text out of a dumped
  DOM. A view that renders every value into a single unreadable column would
  pass, as proof 11 already noted.
- **The inbox does not poll.** It reads once when the view mounts. A held call
  arriving while an approver is looking at the page does not appear until they
  reload, which for a queue somebody is watching is the wrong default. The
  ledger view's poll machinery would carry over, and it is not carried over
  because the row expansion registry it needs is now shared and the change is
  bigger than it looks.

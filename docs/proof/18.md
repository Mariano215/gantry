# Proof 18, three gaps in the ledger

## 1. The claim

`docs/GLOSSARY.md` closes with a list of things the documentation declares and
the code does not do. Three of them were the ledger's.

**`seq` gaps.** `docs/EVENT-SCHEMA.md` said "a gap in `seq` is the signal that
a harness was switched off mid-run", and `docs/CLAUDE-CODE-INTEGRATION.md`
repeated it as the reason the integration is detection rather than prevention.
The verifier did not look at `seq` at all. Two documents carried the claim and
nothing computed it, which is a layer at maturity 3 by this project's own
thesis.

**Consistency proof checking.** `gantry ledger consistency` produced a proof.
Nothing shipped could check one: the checker was a library function and a
property test. A proof a third party is handed and cannot check offline with
the shipped binary is not a proof, it is a blob.

**`ledger.anchor`.** An event kind in the schema, a policy field in
`profile_requirements.ledger.anchoring`, and nothing that anchors anything.

The claim now is that the verifier reports gaps and says what a gap is worth,
that a consistency proof checks from the CLI the same way an inclusion proof
does, and that a `ledger.anchor` event exists because something writes one.

## 2. The attack

1. Punch a real gap in a real run and check the verifier names it. Not by
   deleting a line, which is a different crime the chain already catches, but
   by a run that writes 0, 1, 2 and comes back at 5.
2. Punch no gap in a second run in the same log. A checker that fires on
   everything is as dead as one that never fires.
3. Hand the consistency checker a proof that does not check out. Both shapes:
   a proof element the log never produced, and an old root nobody signed.
4. Rewrite history the way only the log's own writer can, dropping the tail of
   `events.jsonl` and `heads.jsonl` and re-appending under the same ledger key.
   The rewritten log must verify clean, because that is the limit anchoring
   exists for, and the anchored head must catch it.
5. Anchor into the ledger directory. It must be refused. A copy that whoever
   rewrites the log also rewrites detects nothing.
6. Anchor twice to the same path. It must be refused. Overwriting the older
   copy destroys the only thing an anchor is.

## 3. Fault or finding, for a `seq` gap

A finding. Reported, counted, named, exit zero, and `VerifyReport::ok` untouched.

The argument is about what the record can prove. Consider the two ways a hole
in a run's `seq` could arise.

An entry was appended and later removed. The verifier already faults on that,
in three separate places: `prev_hash` stops matching the recomputed leaf of the
entry before, the signed head over the prefix stops matching the recomputed
root, and a truncated tail is reported as having no head covering it. So a
removed entry never reaches the gap check as a mystery; it arrives already
named as an alteration.

Or the event was never written. That is what a hole in `seq` actually is. And
the log cannot tell a harness killed between numbering and appending from a
producer that numbered an event and then failed to write it, because in both
cases the log contains exactly the same bytes, which is to say nothing. Calling
that an alteration would be the verifier asserting something it cannot
distinguish. It would also make `verify` exit non-zero on a log that is
perfectly intact, which trains a reader to ignore the exit status, and an exit
status people ignore is worse than one that stays quiet.

So the gap is printed with what to do about it, and the exit code keeps meaning
"the record was altered". The message says which of the two it is not:

```
seq gap in run run-01: last seq before the gap 2, next seq after it 5, 2
event(s) missing. Fix: this run's record is partial, so read it as evidence of
a harness that stopped writing (check the wrapper's exit path and the hook that
invokes gantry) rather than as an altered log; the chain and the heads verify,
so nothing was removed after append
```

One further restriction, for the same reason. Only interior gaps are reported.
A run whose first recorded `seq` is 4 is not reported as missing its opening,
because where a run starts numbering is the producer's business: `RunCore`
starts at 0, the hand-written traces in this repository start at 1, and a
verifier that guessed would fire on the second kind forever.

## 4. What happened

**Attack 4, the rewrite.** Four honest appends first, so the anchor is shown
accepting growth before it is shown refusing a rewrite:

```
$ gantry ledger verify-anchor $LED /tmp/p18/keep/head-8.json
anchor verified: the log at size 13 is consistent with the head anchored at size 8 in /tmp/p18/keep/head-8.json

Then the writer drops everything after entry 5 from both files and re-appends

```
$ gantry ledger verify $LED

That pair of exit codes is the whole argument for anchoring. The log verifies
clean. Every chain link matches, every head signature checks, the tree recomputes
to the signed root at every size. Five events that happened are gone and
verification has nothing to say about it. The only thing that noticed is a
32-byte root somebody kept somewhere else.

Attack 6 (a second anchor to the same path) and the wrong-kind refusal are in
`tests/ledger.rs`
(`anchoring_refuses_a_destination_inside_the_ledger_and_refuses_to_overwrite`).

## 5. The check, seen red

`ci/run.sh` gained one block, between the offline suite and the policy parity
check. It was proved able to fail twice, by regressing the code it guards and
running the block against the resulting binary.

**Gap reporting regressed** (`pair[1] > pair[0] + 1` widened to `+ 100` in
`seq_gaps`, so the function still runs and reports nothing):

```
== the verifier reports seq gaps, a consistency proof checks from the CLI, and an anchored head catches the rewrite verification alone misses ==
ledger verify did not report the gap punched in run-01: entries: 8. Fix: seq_gaps in src/ledger.rs computes the holes and src/main.rs prints them; docs/EVENT-SCHEMA.md says a gap is the signal a harness was switched off mid-run, so nothing may carry that claim except this check
block exit=1
```

**Anchor verification regressed to the natural wrong implementation.**
`verify-anchor` folded the ledger's own head at the anchored size instead of
the anchored copy, one token different and completely worthless:

```
a rewritten history still agreed with the anchored head: anchor verified: the log at size 9 is consistent with the head anchored at size 8 in /var/folders/.../keep/head.json. Fix: verify-anchor must fold the anchored root through the consistency proof; without that the ledger.anchor event is decoration
block exit=1
```

The second one matters more than the first. That version prints
`anchor verified` on a rewritten log, which is a dead sensor reporting green in
the most convincing possible voice.

Both were reverted, and the gate passes:

```

CLAUDE.md carries 2 [UNENFORCED] marker line(s); gantry scan is expected to report them
ci gate passed
```

## 6. What surprised you

**The proof was the wrong artifact, and adding a checker exposed it.**
`gantry ledger consistency` printed a bare array of sibling hashes. Writing the
checker made it obvious that nobody could ever use that: a consistency proof
is meaningless without the two roots it connects, and the old root has to be a
head the log signed rather than a hash the checker is told to trust. The
subcommand that was missing was not really a checker, it was the producer
emitting half an artifact for nine slices, and nothing noticed because nothing
consumed it. An output format nobody parses is a format nobody has checked.

**Anchoring turned out to be almost no code, because the hard part was already
there.** Building item 2 first was luck rather than judgement. Once a
consistency bundle can be checked against an old head from anywhere, an anchor
is a copy of a head plus the same check, and the entire feature is the choice
of where the copy goes and the honesty of what the payload says. That is the
right ratio: anchoring is not a cryptographic problem, it is a custody problem,
and the code should be small enough to make that obvious.

**Refusing to overwrite an anchor is the more important of the two refusals.**
The destination check (not inside the ledger) is the one you think of. The
overwrite check is the one that matters over time: an operator who anchors to
the same path every day holds exactly one copy, of the newest head, which
detects rewrites of nothing that a fresh proof would not already show. An
anchor is only worth the age of the oldest one still held.

**A gap in `seq` says nothing about which events are missing.** The report says
two events numbered 3 and 4 in `run-01` are absent, and that is all it will ever
say, because the payloads were never written either. There is no hash to expire
against, no envelope to point at. This is the honest shape of detection rather
than prevention, and it is worth saying out loud that "detected" here means
"you now know you are missing something you cannot recover".

## 7. Conformance delta

**No score moved.** Primitive 11 (observability) sits at 3 and the overall at
the minimum across primitives, and `config/scoring.json` has no rule that reads
`ledger.anchor`, a `seq` gap count or a consistency check. Adding one in the
same breath as the feature is what proof 13 records going wrong, so it is not
done here.

What did change is the count of claims carried only by prose. Three entries
leave the "declared, not enforced" list in `docs/GLOSSARY.md` and one arrives:
anchoring is now implemented and its limit is a documented property rather than
an absence.

## 8. What is still a guide

- **`anchoring: none` is still the only setting anything reads.**
  `profile_requirements.ledger.anchoring` names `object_store`, `rfc3161` and
  `notary`. `gantry ledger anchor` writes a file copy and nothing dispatches on
  the profile's declared kind, so a profile demanding `rfc3161` gets no anchor
  and no refusal. The anchor command is an operator action, not a scheduled
  obligation the policy enforces.
- **Nothing schedules an anchor.** There is no daily anchor, no reminder, and
  no check that the newest anchor is not six months old. An anchor nobody takes
  is the same as no anchor, and this repository currently relies on somebody
  remembering.
- **The anchor is only as independent as its destination.** The command refuses
  the ledger directory and refuses to overwrite, which is the most a local
  process can enforce. It cannot tell a WORM mount from a sibling directory on
  the same disk, and it says so in the event payload rather than pretending.
- **`verify-anchor` reads the ledger's current public key.** A writer who
  rewrites the log and also rotates `keys/ledger.pub` is caught, but reported as
  a head signature failure rather than as a rewrite. Correct outcome, confusing
  message. A verifier handed the key alongside the anchor would read better.
- **The `ledger.anchor` event is unsigned and its authority is `unobserved`.**
  `gantry ledger anchor` reads no policy and holds no actor key, in keeping with
  every other `ledger` subcommand, so it writes what it cannot observe as
  `unobserved` rather than guessing a profile. An anchor taken from inside a
  run would be attested; this one is not, and `gantry ledger verify` counts it
  as an absent attestation rather than a verified one.
- **A `seq` gap is not shown in the console.** `src/console.rs` builds the
  verify view's JSON field by field from the report and was not in scope for
  this work, so an operator watching the console sees a clean log and reads the
  gap only from the CLI. The claim lives in `gantry ledger verify` and in the
  CI check.

# Proof 12, the permission-mode hook

## 1. The claim

`CLAUDE_PERMISSION_MODE` is set automatically, not by hand: a PreToolUse hook
reads the real permission mode Claude Code already puts on its own hook
input and injects it into any Bash command that invokes gantry, so
`authority.permission_mode` records the observed mode instead of
`"unobserved"`, and a mode that diverges from the tracked
`permissions.defaultMode` lands in `authority.diverged` as
`host_permissions.permission_mode` on the very run that saw it.

## 2. The attack

Executed by `docs/proof/12-run.sh` against the tracked
`.claude/hooks/permission-mode.sh` and `.claude/settings.json`.

1. Confirm the pre-existing gap: with `CLAUDE_PERMISSION_MODE` unset, the
   observed mode records `"unobserved"` and never divergence, which is the
   correct behaviour for an unwrapped session but the whole reason the hook
   is needed.
2. Feed the hook fixture input matching what Claude Code actually sends a
   PreToolUse hook: a command with no `gantry` in it must pass through
   untouched (negative control), and a `gantry` command with an observed
   `permission_mode` must come back rewritten with
   `export CLAUDE_PERMISSION_MODE=...;` prefixed.
3. Actually run the rewritten command under a mode (`bypassPermissions`)
   that diverges from the tracked declaration (`.claude/settings.json`
   declares no `permissions.defaultMode`, so the tracked value is the
   implicit `"default"`), and read the resulting `run.open` event's
   authority off the ledger.
4. Run the same path under a mode that matches the tracked declaration
   (`default`) and confirm no divergence is reported.

Reproduce with:

```
cargo build
zsh docs/proof/12-run.sh
```

## 3. What happened

Workdir `/tmp/gantry-proof12.ROc5Cp`. All output verbatim.

Attack 1, the pre-existing gap, unobserved and not treated as divergence:

```
{"permission_mode":"unobserved","diverged":["host_permissions.settings_hash"]}
```

Attack 2 setup, the hook's own behaviour:

```
-- a command with no gantry in it: left untouched --
{}
-- a gantry command, observed mode bypassPermissions: rewritten to export it --
"export CLAUDE_PERMISSION_MODE='bypassPermissions'; ./target/debug/gantry run config/providers.json local /tmp/gantry-proof12.ROc5Cp/ledger"
```

Attack 2, the rewritten command actually run, and the divergence landing on
the ledger:

```
{"permission_mode":"bypassPermissions","diverged":["host_permissions.settings_hash","host_permissions.permission_mode"]}
host_permissions.permission_mode is in authority.diverged: the hook-observed mode disagreed with the tracked declaration, and the event says so
```

Attack 3, a matching mode, no divergence:

```
{"permission_mode":"default","diverged":["host_permissions.settings_hash"]}
```

The ledger the divergence was read from still verifies:

```
entries: 4
```

`ci/run.sh` runs the same hook-fixture checks (`ci/permission-mode-hook`)
on every push:

```
== permission-mode hook injects the observed mode into gantry commands, leaves everything else alone (ci/permission-mode-hook) ==
hook injects the observed mode, leaves unrelated and unobserved commands untouched, and the export propagates through the rewritten command
```

## 4. What surprised you

`host_permissions.settings_hash` diverges in every attack above, including
attack 3 where the permission mode matches. That divergence is real and
expected right now: `.claude/settings.json` changed on disk (the hook is
being wired in this same slice) and has not yet been committed, so the
on-disk file does not match `git show HEAD:.claude/settings.json`. It
resolves the moment this slice is committed, and it is a different signal
from the one this proof is about (`settings_hash` names a content edit,
`permission_mode` names a running-mode mismatch); the two can diverge
independently, which the event correctly shows by listing them separately.

The hook cannot literally export an environment variable into the Claude
Code process itself; no hook can, since it runs as a disconnected child
process. What it can do, and what Claude Code's PreToolUse contract
actually offers, is rewrite the tool_input of the very Bash call about to
run (`updatedInput.command`), so the `export ...;` prefix lives inside the
same `sh -c` invocation as the command it is protecting. That is why the
hook targets commands containing `gantry` rather than every Bash call: it
would be pointless (and noisy in the transcript) to rewrite commands that
never reach `permission_mode_check`.

## 5. Conformance delta

Primitive 12 (Governance): the `permission_mode` half of the authority
declaration moves from "recorded when a wrapper happens to set the
variable" to "recorded on every gantry invocation a Claude Code session
makes," since the hook is now the wrapper and it is wired into the tracked
settings file rather than left to whoever remembers to export the variable
by hand. This does not change `config/scoring.json`'s primitive 12 rule (it
already credits a named `policy.decision` deny at level 3); the delta is in
how reliably `authority.permission_mode` carries a real value instead of
`"unobserved"`, which is the gap `docs/proof/00.md` finding (a) named.
Overall level unaffected by this slice.

## 6. What is still a guide

The hook only fires for Bash commands whose text contains the literal
substring `gantry`. A command that reaches the binary indirectly (a Makefile
target, a shell alias, a script that `exec`s it under a different visible
name) would not be rewritten and would fall back to `"unobserved"`. This is
a deliberate, narrow match, not a broken one: it is scoped precisely because
the only consumer of `CLAUDE_PERMISSION_MODE` is `permission_mode_check`,
which only runs inside gantry. Nothing here is `[UNENFORCED]`: the CLAUDE.md
marker for this slice is removed, because the hook now runs, is wired in
version control, and `ci/run.sh` checks its behaviour on every push.

# Proof 17, a profile that cannot be provided refuses to start

## 1. The claim

`docs/POLICY-SCHEMA.md` described three profiles across eleven rows. One of
them ran. The rest were prose, including the row the document itself said
carried the weight:

> `on_unavailable: refuse` is why `regulated` does not quietly become `laptop`
> when the HSM is missing: the control plane fails to start and says which
> requirement was unavailable.

Nothing read the field. A `regulated` policy declaring `microvm` isolation,
`oidc` identity, `rfc3161` anchoring and `hsm` key custody started on this
laptop and ran under seatbelt, local identity, an unanchored file and a
software seed, and said nothing. The row that existed to prevent silent
degradation was itself the silent degradation.

The claim now is that a requirement nothing on the machine can provide either
stops the run and names itself, or is written on the ledger. Never neither.

**Availability is not divergence, and the two are separate checks.**
Divergence is one declared value against the one value observed now: declared
`microvm`, observed `seatbelt`. Availability asks whether anything on this
machine could meet the declaration at all. `policy::availability_check` takes
the values the caller already observed as arguments and reads no system state,
so it is not a second observer: `Providable` holds a set per field, and a host
that can boot a microvm answers yes for microvm even while a given run sits
inside seatbelt. That case is a divergence for `gantry drift` to report and
this check stays silent on it (`tests/profiles.rs`,
`a_declaration_the_host_can_provide_is_available_even_when_this_run_diverges`).

## 2. The attack

1. A `regulated` policy with `on_unavailable: refuse` on this machine. It must
   refuse, and the fault must name every unavailable requirement, not the
   first one, and not a count.
2. The refused run must append nothing. A refusal that leaves half a run on
   the ledger is a worse record than no check.
3. The same declarations with `on_unavailable: degrade`. The run must start,
   and the shortfall must be on `run.open`. A degrade that swallows the
   shortfall is the failure this work exists to close, one field further down.
4. The tracked `laptop` policy must be untouched: it must start, with an empty
   shortfall list. A check that refused the tracked policy would be measuring
   the machine rather than the declaration.
5. A stance the code does not recognise (`"Refuse"`) must refuse rather than
   fall through to degrade. One typo must not turn the row back into prose.
6. The gateway must refuse the same profile. Two run opens means two doors,
   and a check on one of them is a check on neither.
7. The CI check must be shown red. A check never seen fail is a dead sensor
   reporting green.

## 4. What surprised you

**The correct result is that `regulated` does not run here.** The first
instinct on seeing the refusal was that the check was too strict, because it
makes a profile in the tracked schema unusable on the machine the project is
developed on. That instinct is the defect. Nothing in this codebase provides a
microvm, OIDC, RFC 3161 anchoring or an HSM, so a `regulated` profile that
started here would be a `laptop` wearing the word. The refusal is the feature,
and the awkwardness of it is the honest cost of having written the row down.

**Deleting the table was more of the work than writing the check.** Eleven
rows, one enforced. After implementing `on_unavailable` there were five, and
three of the deletions were not "not built yet" but "read by no code at all":
`isolation.scores`, `rung_default` and `identity.fallback_permitted` appear in
the schema, in the tracked policy, and in no source file. `isolation.scores`
had a paragraph of its own claiming the laptop profile caps the score at 3 "by
declaration". The scorer never reads it. That paragraph is gone, and the cap it
described comes from telemetry, which is the invariant the paragraph was
quietly contradicting.

**The unrecognised-stance branch was not in the plan and is the sharpest part
of the check.** `on_unavailable` is a two-value field read with a string
compare, and the natural implementation treats anything that is not `refuse` as
`degrade`. That means `"Refuse"`, `"refuse "` or `"strict"` all silently
degrade, in the one field whose entire purpose is to stop silent degradation.
It refuses on every run now, shortfall or not.

**The seam had to be drawn in the signature, not in a comment.**
`availability_check` takes what the caller observed. It has no way to read the
sandbox, the identity source or the key registry, so it cannot grow into an
observer by accident, and the drift work landing beside it has nothing to
collide with. The one accessor added is `sandbox::active_backend()`, which
answers what backend this host can provide without building a sandbox, because
run open needs that answer before it appends anything.

## 5. Conformance delta

**No primitive moved.** Primitive 12 (authority and policy) is scored from
ledger telemetry, and `config/scoring.json` has no rule that reads the
`unavailable` field on `run.open`. Writing one in the same breath as the
feature is the mistake proof 13 records, so it is not part of this work: a rule
crediting a level would have to name the control running, and
`docs/proof/08-run.sh` would have to exercise a refused profile, or the rule
lands and nothing changes.

What did move is the document. `docs/POLICY-SCHEMA.md` claimed eleven profile
behaviours and could support one. It now claims five and names the file and
test behind each. Four rows were deleted as unbuilt and are listed as such
under the table, which is a lower number honestly stated rather than a higher
number asserted, and by this project's own thesis the eleven-row version was
capping primitive 12 at 3 while reading as coverage.

## 6. What is still a guide

- **`Providable::for_this_build` hardcodes three of its four answers.**
  Identity, anchoring and key custody are stated as constants, because this
  build implements exactly one of each and there is nothing to observe. They
  are honest today and they will rot the moment one of the three grows a
  second implementation, with nothing to catch it but the reader. The isolation
  field is the shape the other three should take: observed, passed in.
- **Availability is checked at run open and never again.** A backend that
  disappears mid-run is not noticed until the next run opens. That is the same
  cadence as the attestation check beside it, and it is the drift check on a
  schedule, not this one, that would close it.
- **`egress.allow` has no availability question and gets none.** An allowlist
  entry naming a host that does not resolve is a declaration this check treats
  as met, because the sandbox will enforce the allowlist whether or not the
  host exists. Whether an unreachable allowlist entry should be a shortfall is
  an open question and needs a network probe, which the offline suite will not
  have.
- **`isolation.scores`, `rung_default` and `identity.fallback_permitted` still
  load.** They are read by nothing and are now named as such under the table
  rather than deleted from the shape, because a policy carrying them still has
  to load. Removing them from the schema is a `policy_version` bump and a
  migration for every tracked policy, which is its own piece of work.
